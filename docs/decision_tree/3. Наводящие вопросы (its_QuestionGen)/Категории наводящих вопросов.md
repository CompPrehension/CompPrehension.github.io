Страница [[../1. Модели (its_DomainModel)/Дерево решений/Соглашения о метаданных.md#ключи-наводящих-вопросов|«Соглашения о метаданных»]] описывает ключи, которые могут быть использованы для наводящих вопросов с их кратким предназначением. Здесь же представлена подробная информация, как именно ключи используются в наводящих вопросах

## Автомат вопросов и стратегии

Диалог представлен **автоматом** (`QuestionAutomata`) - графом состояний `QuestionState`. Состояния бывают четырёх видов:

| Вид состояния              | Что делает |
| -------------------------- | ---------- |
| `GeneralQuestionState`     | Собственно задаёт вопрос: возвращает `Question` (текст, варианты, тип), а по ответу выдаёт объяснение и следующее состояние. Наследники - `SingleChoiceQuestionState` (один вариант), `MultipleChoiceQuestionState` (несколько), `AggregationQuestionState` (сопоставление). |
| `SkipQuestionState`        | Вопрос не задаётся: состояние сразу возвращает объяснение и следующее состояние. Так реализованы «пропуски» и служебные реплики. |
| `RedirectQuestionState`    | «Незавершённый хвост» автомата. Пока автомат не финализирован, такие состояния указывают в никуда; `QuestionAutomata.finalize(state)` замыкает их все на переданное состояние. |
| `EndQuestionState`         | Конец диалога (`nextState == null`). Передаётся снаружи при `buildAndFinalize`. |

Автомат для одной [ветви мысли](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Дерево%20(граф)%20решений.md) строит **стратегия** (`QuestioningStrategy`). В модуле их три, и они вложены друг в друга:

1. **`VariableValueStrategy`** - вопросы о значениях переменных, объявленных узлами [`FindActionNode`](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Узлы.md#Действие%20поиска%20(найти%20объект%20и%20запомнить),%20FindActionNode) внутри ветви.
2. **`SequentialStrategy`** - последовательный обход ветви: вопросы к узлам и к переходам между ними. Помимо автомата возвращает две карты - `nodeStates` (состояние, соответствующее вопросу *в* узле) и `preNodeStates` (состояние вопроса о переходе *к* узлу); они нужны следующей стратегии.
3. **`FullBranchStrategy`** - стратегия «по умолчанию» (`QuestioningStrategy.defaultFullBranchStrategy`), которая склеивает первые две:
   - сначала автомат `VariableValueStrategy`;
   - если у ветви **больше одного** потенциального конечного узла - [вопрос о конечном узле рассуждений](#Вопрос%20о%20конечном%20узле%20рассуждений), и уже из него - переход в нужную точку автомата `SequentialStrategy`;
   - если конечный узел ровно один - сразу автомат `SequentialStrategy`;
   - в конце - служебное состояние-пропуск с репликой **«Итак, мы обсудили, почему `<description ветви>`.»**, где `description` берётся с фактическим результатом ветви.

Именно `FullBranchStrategy` рекурсивно применяется ко вложенным ветвям - телу цикла, веткам агрегации и т.д.

## Общие правила формирования текстов

Эти правила действуют для всех категорий, поэтому ниже они не повторяются.

**Шаблоны.** Любой текст берётся из метаданных элемента графа с учётом кода локализации (`RU.question`, `EN.question`) и интерпретируется как [[./Шаблонизация текстов.md|шаблон]] с доступом к [выражениям](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Выражения.md). В шаблон могут подставляться контекстные переменные:

- `branchResult` - для ключей `description` и `nextStepBranchResult`; кроме того, для них сначала ищется уточнённый ключ `<ключ>_correct` / `<ключ>_error` / `<ключ>_null`, и только потом общий;
- `checked` - объект, выбранный учащимся, для `explanation` категории ошибки поиска.

**Автогенерация.** Если у `QuestionNode` или `WhileCycleNode` нет ключа `question`, текст вопроса порождается автоматически из выражения узла (`QuestionGeneratorFabric`, пакет `formulations.v2.generation`). Аналогично при отсутствии `text` / `explanation` у перехода порождаются формулировка варианта ответа и объяснение. Поддерживаются не все виды выражений: если генератор не знает такого выражения, текст остаётся не сформированным (и отсутствие обязательного ключа приведёт к ошибке времени выполнения). Если включён `GigaChatAPI`, готовая формулировка верхнего уровня дополнительно прогоняется через LLM-«причёсывание».

**Объяснение ответа.** Для вопросов-наследников `CorrectnessCheckQuestionState` объяснение единообразно:

- правильный ответ - системный текст **«Верно.»**;
- неправильный - объяснение, привязанное к варианту ответа; если его нет - системное **«Это неверно.»**

> [!note]
> Объяснение неправильного ответа в большинстве категорий **одно на весь вопрос** и строится по *правильному* исходу, а не по выбранному учащимся. Исключения - вопросы о значении переменной и MUTEX-агрегация, где объяснение зависит от выбранного варианта.

**Когда вопрос не задаётся.** Состояние может «схлопнуться» в пропуск:

- **тривиальная ветвь.** Ветвь считается тривиальной, если её первый узел - не связующий, либо все его потомки - узлы результата. В такой ветви не задаются вопросы к узлам `QuestionNode`, `TupleQuestionNode`, `FindActionNode`, не задаётся вопрос о начале ветви и не задаётся вопрос об общем результате узла AND/OR-агрегации;
- **тривиальный узел вопроса.** При `isSwitch` вопрос пропускается молча; при истинном `trivialityExpr` - с текстом из ключа `triviality` (если он задан);
- **единственный вариант ответа.** Если у вопроса с одиночным выбором остался ровно один вариант, вопрос не задаётся, ответ засчитывается автоматически, а вместо объяснения выдаётся `explanationIfSkipped` (по умолчанию ничего).

**Состояние диалога** (`QuestioningSituation`) хранит: обсуждённые переменные (`discussedVariables`), данные ответы по id состояний (`givenAnswers`) и *предполагаемые* учащимся результаты ветвей (`assumedResults`). Последние определяют формулировки вида «Почему вы считаете, что …».

## Вопросы о значении переменной

Строятся `VariableValueStrategy` **до** обхода самой ветви. Стратегия собирает все `FindActionNode` ветви и оставляет только **решающие** переменные - те, которые используются в выражении какого-либо `QuestionNode`, либо объявлены узлом с переходом «не найдено» (`nextIfNone`). Для каждой такой переменной сначала рекурсивно задаются вопросы о переменных, от которых зависит её выражение поиска.

**Вопрос повторяет само действие узла:**

- **Текст:** ключ `question` узла `FindActionNode`.
- **Варианты ответа:** локализованные имена (`localizedName`) объектов, которые могли бы быть найдены. Объекты делятся рассуждателем на корректный и ошибочные - последние группируются по [категориям ошибок поиска](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Способы%20описания/LOQI2.md#категории-ошибок-поиска). Дополнительно добавляется вариант «ничего не найдено»: текст берётся из `explanation` перехода `nextIfNone` (с заглавной буквы), а если такого перехода нет - системный текст **«Невозможно найти.»**
- **Объяснение неправильного ответа:** `<объяснение ошибки> <указание на правильный вариант>`, где
  - *объяснение ошибки* - `explanation` категории ошибки поиска, которой соответствует выбранный объект; в шаблон подаётся контекстная переменная `checked` с этим объектом. Для варианта «ничего не найдено» вместо этого берётся системное «Это неверно.»;
  - *указание на правильный вариант* - **«В данной ситуации `<explanation правильного перехода узла>`.»**
- **Побочный эффект:** выбранный объект запоминается в `discussedVariables`, чтобы вопрос не задавался повторно.

Вопрос **пропускается целиком**, если переменная уже обсуждалась, если узел не встретился в трассе решения текущей ветви, или если список вариантов пуст.

## Вопрос о конечном узле рассуждений

Задаётся `FullBranchStrategy` **только если** у ветви больше одного потенциального конечного узла (узла, из которого возможен переход в узел результата, либо агрегации с неполным набором переходов).

- **Текст:** если по ходу диалога уже зафиксирован предполагаемый результат ветви - **«Почему вы считаете, что `<description ветви с этим результатом>`?»**; если нет - системное **«Что из перечисленного применимо в данной ситуации?»**
- **Варианты ответа:** ключ `endingCause` каждого потенциального конечного узла.
- **Объяснение:** системное **«Давайте разберемся.»** для любого ответа - этот вопрос не оценивается как верный/неверный.
- **Переход:** вычисляется **наименьший общий предок** (LCA) выбранного и правильного конечных узлов. Диалог продолжается с вопроса *в* этом узле (`nodeStates`), а если LCA не совпадает с выбранным узлом - с вопроса *о переходе к* нему (`preNodeStates`). Так разбор начинается ровно с той развилки, где пути разошлись.

## Вопросы к узлам

### Узел вопроса, `QuestionNode`

- **Текст:** ключ `question`, иначе автогенерация по выражению узла `expr`.
- **Варианты ответа:** по одному на переход из узла; текст - ключ `text` перехода, иначе автогенерация ответа по `expr` и ключу перехода, иначе локализованное представление самого ключа перехода.
- **Объяснение неправильного ответа:** ключ `explanation` **правильного** перехода, иначе автогенерация объяснения по `expr`.
- Далее - [вопрос о переходе](#Вопросы%20о%20переходах%20между%20узлами).

### Вопрос с кортежем, `TupleQuestionNode`

Один узел порождает **цепочку** вопросов - по одному на каждую часть кортежа, в порядке объявления частей.

- **Текст:** ключ `question` соответствующей части.
- **Варианты ответа:** ключ `text` каждого из возможных исходов части, иначе локализованное представление значения исхода.
- **Объяснение неправильного ответа:** ключ `explanation` правильного исхода части.
- После последней части - служебный пропуск, который по кортежу фактических ответов выбирает переход из узла и переходит к вопросу о нём.

### Действие поиска, `FindActionNode`

Вопрос **не задаётся** - смысл узла уже раскрыт на этапе вопросов о значении переменной. Вместо вопроса выдаётся реплика:

> Мы уже говорили о том, что `<explanation правильного перехода узла>`.

После неё - вопрос о переходе.

### Узел последовательной агрегации (цикла), `WhileCycleNode`

Порождает несколько связанных состояний:

1. **Вопрос об условии цикла.** Текст - ключ `question` узла, иначе автогенерация по `conditionExpr`. Варианты ответа строятся по переходам узла: `text` перехода, иначе автогенерация ответа по `conditionExpr`, иначе локализованное представление ключа перехода. Объяснение неправильного ответа - `explanation` правильного перехода, иначе автогенерация.
2. **Вопрос «что дальше» после проверки условия.** Текст - `nextStepQuestion` соответствующего перехода, иначе ключ `bodyNextStepQuestion` самого узла, иначе системное «Какой следующий шаг необходим для решения задачи?». Варианты: `asNextStep` потенциально достижимых узлов; формулировки красного и зелёного результата ветви (`nextStepBranchResult`, иначе «Можно заключить, что `<description ветви>`.»); плюс отдельный вариант **«Необходимо проверить, что `<description тела цикла>`»** - он и является правильным, если условие выполнилось.
3. **Автомат тела цикла** - строится `FullBranchStrategy` по `thoughtBranch` узла.
4. **Вопрос «что дальше» после итерации тела** - по результату итерации. Текст - `nextStepQuestion` перехода, иначе системный текст. В варианты, помимо достижимых узлов и результатов ветви, добавляется **сам узел цикла** (то есть «пойти на следующую итерацию»); при результате итерации `null` управление возвращается к вопросу об условии.

> [!note]
> Ключ `bodyNextStepExplanation` в коде **объявлен, но нигде не используется**: в качестве объяснения на шаге 2 подставляется `nextStepExplanation` перехода, а при его отсутствии - текст `bodyNextStepQuestion`. Опираться на `bodyNextStepExplanation` пока нельзя.

### Узлы агрегации

Для [`BranchAggregationNode`](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Узлы.md#Узел%20агрегации%20по%20ветвям,%20BranchAggregationNode) и [`CycleAggregationNode`](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Узлы.md#Узел%20агрегации%20в%20цикле%20по%20объектам,%20CycleAggregationNode) вопросы строятся **общим кодом**: различия спрятаны за `AggregationHelper`, который отвечает на вопросы «какие тут ветки», «как их описать» и «каков результат каждой». Для агрегации по ветвям «веткой» является `ThoughtBranch`, для агрегации в цикле - объект-значение переменной цикла (описание берётся у тела цикла при подставленной переменной).

Набор вопросов определяется **методом агрегации**:

| Метод агрегации | Что задаётся |
| --------------- | ------------ |
| `AND`, `OR`     | вопрос-сопоставление о результатах веток, затем вопрос об общем результате узла |
| `MUTEX`         | один вопрос о том, какая из веток применима |
| `HYP`           | **не реализовано** - построение автомата упадёт с `TODO("HYP aggregation not supported yet")` |

#### Дополнительный вопрос для `CycleAggregationNode`

Перед вопросами о самой агрегации задаётся **вопрос с множественным выбором** об объектах, перебираемых циклом:

- **Текст:** ключ `question` узла.
- **Варианты:** локализованные имена объектов; правильные - те, что проходят предикат поиска, неправильные берутся из [категорий ошибок поиска](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Способы%20описания/LOQI2.md#категории-ошибок-поиска) узла.
- **Объяснение:** при полном совпадении множеств - «Верно.»; иначе «Это неверно.» и, каждое с новой строки, объяснения для всех пропущенных и всех лишних вариантов (для лишних - `explanation` категории ошибки, для пропущенных - системное «`<объект>` also fits the criteria»).

#### Агрегация `AND` / `OR`

**1. Вопрос о результатах веток** - это вопрос типа `matching` (**сопоставление**, а не множественный выбор):

- **Текст:** системное **«Пожалуйста, сопоставьте ответы»**.
- **Сопоставляемые элементы:** описания всех веток (`description` с `branchResult = CORRECT`).
- **Варианты сопоставления:** «Верно» / «Неверно».
- **Объяснение:**
  - всё верно - **«Вы верно оценили ситуацию, однако это значит, что `<description узла с фактическим результатом>` - из-за того, что `<описания веток, давших этот результат>`»**;
  - есть неверно отмеченные - **«Это неверно, поскольку `<описания этих веток с их настоящими результатами>`.»**;
  - есть не отмеченные, хотя следовало - **«Вы также не упомянули, что `<описания веток>` - это влияет на ситуацию в данном случае.»** (или отдельной репликой, если неверно отмеченных не было).
- Ветки, отмеченные как `null`, не считаются ошибкой, если метод агрегации уже определил результат узла без них (короткое замыкание `AND` при ошибке и `OR` при успехе).

> [!note]
> Ключ `nullFormulation` узла агрегации задуман как формулировка третьего варианта сопоставления («не влияет») для веток, способных дать `null`. Из-за ошибки в коде (результат `plus` не присваивается) этот вариант **фактически не добавляется**, и сопоставление всегда идёт по двум вариантам.

**2. Вопрос об общем результате узла** (пропускается, если текущая ветвь тривиальна):

- **Текст:** **«Верно ли, что `<description узла с branchResult = CORRECT>`?»**
- **Варианты ответа:** «Верно» / «Неверно», и «Не влияет» - если узел может дать `null`.
- **Объяснение неправильного ответа** - системное, собирается из метода агрегации и описаний веток: *«Это неверно. Чтобы понять, что `<описание узла>`, все (для AND) / хотя бы один (для OR) из описанных выше факторов (`<описания веток>`) должны выполняться. …»*
- Далее - вопрос о переходе из узла.

**3. Углубление в ветку.** Если на вопросе 1 были ошибки, задаётся вопрос **«В чем бы вы хотели разобраться подробнее?»**. Варианты - **«Почему `<description ветки с её настоящим результатом>`?»** для всех веток, чей настоящий результат не совпал с отмеченным учащимся. Объяснение - «Давайте разберемся.». По выбранной ветке запускается её собственный автомат (`FullBranchStrategy`); если у ветки нет вопросов, происходит переход дальше без разбора.

#### Агрегация `MUTEX`

Один вопрос о том, какая из взаимоисключающих веток применима - именно он соответствует тому, что в старой документации называлось «узлом предрешающих факторов».

- **Текст:** системное **«Что из перечисленного применимо в данной ситуации?»**
- **Варианты ответа:** для каждой ветки - её `description` для каждого возможного (кроме `null`) результата этой ветки; плюс вариант **«Ничто из вышеперечисленного не применимо»**.
- **Объяснение неправильного ответа:** **«Это неверно. В данной ситуации `<description правильной ветки с её результатом>`.»**, либо «Это неверно. Ничто из вышеперечисленного не применимо», если применимых веток нет.
- **Переход:** если выбрана неправильная ветка и у неё есть вопросы - диалог углубляется в эту ветку, чтобы разобрать, почему она не применима; после выхода (или сразу, если разбирать нечего) - переход к вопросу о переходе из узла.

## Вопросы о переходах между узлами

### Переход из узла, `Outcome`

Задаётся после каждого узла, породившего вопрос (а также после узлов-пропусков).

- **Текст:** ключ `nextStepQuestion` перехода, соответствующего правильному ответу; при отсутствии - системное **«Какой следующий шаг необходим для решения задачи?»**
- **Варианты ответа:**
  - `asNextStep` всех узлов, потенциально достижимых из текущего (узлы результата из этого списка исключаются);
  - плюс по варианту на каждый результат ветви: `nextStepBranchResult` перехода с соответствующим `branchResult`, иначе **«Можно заключить, что `<description текущей ветви>`.»**. Вариант для результата `null` добавляется, только если ветвь в принципе может его дать.
- **Объяснение неправильного ответа:** ключ `nextStepExplanation` перехода. Если ключа нет, объяснения не будет вообще (отобразится системное «Это неверно.»), поэтому ключ рекомендуется задавать.

### Переход к первому узлу ветви, `ThoughtBranch`

Задаётся в начале разбора ветви (кроме тривиальных ветвей).

- **Текст:** ключ `nextStepQuestion` ветви, иначе **«С чего надо начать, чтобы проверить, что `<description ветви с branchResult = CORRECT>`?»**
- **Варианты ответа:** `asNextStep` узлов, которые потенциально могут быть первыми в ветке. Варианты для результатов ветви **не добавляются** - заканчивать ветку в самом начале бессмысленно.
- **Объяснение неправильного ответа:** ключ `nextStepExplanation` ветви. В отличие от переходов, здесь ключ **обязателен**: при его отсутствии построение вопроса упадёт с ошибкой.

## Чего в модуле нет

- **Узлы `ProcedureCallNode` и `BranchResultRedirectingNode`** (а с ними и [субинтерпретаторы](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Субинтерпретаторы.md)) не поддерживаются
- **Агрегация `HYP`** не реализована.
- **Вариант «не влияет»** в вопросе-сопоставлении для AND/OR-агрегации не добавляется (см. примечание выше), а ключ `bodyNextStepExplanation` не используется.
