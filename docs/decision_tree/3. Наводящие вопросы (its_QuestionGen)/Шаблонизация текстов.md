Все тексты, которые система показывает учащемуся - формулировки наводящих вопросов, варианты ответа, объяснения ошибок - хранятся не в коде, а в [метаданных](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Соглашения%20о%20метаданных.md) элементов [графа мыслительных процессов](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Дерево%20(граф)%20решений.md). Но текст «Операнд ещё не вычислен» бесполезен, если не сказать, *какой* операнд. Поэтому строки метаданных - не просто строки, а **шаблоны**: в них можно вставлять [выражения](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Выражения.md), вычисляемые по конкретной ситуации.

Эта страница описывает синтаксис таких шаблонов, что в них доступно и как отлаживать результат.

> [!info] Где это реализовано
> Механизм шаблонов - внешняя библиотека [JavaStringTemplating](https://github.com/Max-Person/JavaStringTemplating). `its_QuestionGen` подключает к ней собственный разборщик интерполяций (`OperatorTemplateParser`), благодаря которому **внутри интерполяции пишется LOQI-выражение**, а не язык выражений самой библиотеки. Точка входа - `TemplatingUtils.interpret(...)`.

## Где применяются шаблоны

Шаблоном интерпретируется **любой** локализованный текстовый ключ метаданных, читаемый `its_QuestionGen`: `question`, `asNextStep`, `endingCause`, `description`, `text`, `explanation`, `nextStepQuestion`, `nextStepExplanation`, `nextStepBranchResult`, `triviality`, `nullFormulation` и остальные из раздела [«Ключи наводящих вопросов»](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Соглашения%20о%20метаданных.md#ключи-наводящих-вопросов).

Отдельно стоит ключ `explanation` [узлов результата](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Узлы.md#узлы-результатов-branchresultnode): его читает не `its_QuestionGen`, а CompPrehension (`DecisionTreeReasonerBackend`) - при формировании объяснения к ответу учащегося. Но интерпретируется он **тем же самым** `TemplatingUtils.interpret`, так что весь синтаксис ниже применим и к нему.

> [!warning]
> Из этого правила есть одно историческое исключение. Домен `objects-scope-domain` разбирает `explanation` собственным кодом (`GenerateErrorTextForScopeObjects.generateMessage`) с упрощённым синтаксисом `{X->rel.prop}` - без `$` и без выражений. Это локальный костыль конкретного домена; в новых доменах так делать не нужно.

## Синтаксис

### Интерполяции

```groovy
RU.explanation = "Операнд ${X} ещё не вычислен";
```

Шаблон - это произвольный текст, в котором `${ ... }` обозначает **интерполяцию**: содержимое вычисляется и подставляется в текст вместо себя.

Есть краткая форма без фигурных скобок - `$Имя` - если интерполируется только имя переменной:

```groovy
RU.explanation = "Операнд $X ещё не вычислен";  // то же самое
```

> [!important]
> Внутри `${ ... }` пишется **LOQI-выражение** - см. [«Выражения»](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Выражения.md). Это не отдельный «язык шаблонов»: доступно ровно то, что доступно в выражениях узлов графа, и **только** это. В частности, в LOQI **нет арифметики** - `${1 + 2}` не скомпилируется.

Фигурные скобки внутри интерполяции считаются парными, поэтому выражения со скобочными конструкциями (`find`, `forAll`, блоки) работают:

```groovy
RU.text = "${find op: Operator { op.state == State:unevaluated }}";
```

### Модификаторы

Сразу после `${ ... }` можно указать в квадратных скобках список **модификаторов** - функций, применяемых к уже полученной строке:

```groovy
RU.asNextStep = "Необходимо проверить, нужен ли ${X}[case('д')] левый операнд";
```

Модификаторы перечисляются через запятую и применяются слева направо; аргументы - только литералы (строки, числа, булевы значения):

```groovy
"${X}[case(\"р\")]"
```

Сейчас в `its_QuestionGen` зарегистрирован **один** модификатор:

| Модификатор  | Аргументы | Что делает |
| ------------ | --------- | ---------- |
| `case(падеж)` | код падежа - строка | Склоняет полученную строку по падежу с помощью библиотеки `padeg`. |

Коды падежей (регистр не важен, допускается несколько написаний):

| Падеж         | Коды |
| ------------- | ---- |
| именительный  | `и`, `им`, `и.п.`, `им.п.`, `n`, `nom` |
| родительный   | `р`, `род`, `р.п.`, `род.п.`, `g`, `gen` |
| дательный     | `д`, `дат`, `д.п.`, `дат.п.`, `d`, `dat` |
| винительный   | `в`, `вин`, `в.п.`, `вин.п.`, `a`, `acc` |
| творительный  | `т`, `тв`, `т.п.`, `тв.п.`, `i`, `ins` |
| предложный    | `п`, `пр`, `п.п.`, `пр.п.`, `p`, `pre` |

Склонение - **русскоязычная** механика; в `EN.`-шаблонах модификатор `case` смысла не имеет.

> [!warning] Две ловушки модификаторов
> 1. Модификаторы работают **только с полной формой** `${ ... }`. В записи `$X[case('д')]` скобки останутся обычным текстом и попадут в вывод как есть.
> 2. Между `}` и `[` **не должно быть пробела** - иначе `[...]` тоже станет обычным текстом.
>
> Неизвестное имя модификатора - не молчаливая ошибка, а исключение времени выполнения (`IllegalArgumentException: ... could not find a suitable method`).

### Экранирование символа `$`

Символ `$` в шаблонах служебный, и обращаться с ним надо аккуратно:

- одиночный `$`, за которым не идёт имя или `{`, **молча выбрасывается** из текста (`"one $ two"` → `"one two"`);
- запись `\$` пропускает `$`, но **обратный слэш при этом остаётся** в выводе (`"цена \$5"` → `"цена \$5"`).

Полноценного экранирования нет, поэтому символ `$` в тексте для учащегося лучше не использовать вовсе.

## Что доступно внутри интерполяции

### Переменные графа мыслительных процессов

Пишутся просто именем (по конвенции - `PascalCase`) и берутся из текущей [ситуации](../2.%20Вычисления%20(its_Reasoner)/Трассы%20рассуждения.md) - `LearningSituation.decisionTreeVariables`:

```groovy
"Операнд ${X} ещё не вычислен"
```

Это то же самое, что [переменная дерева решений](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Выражения.md#переменная-дерева-решений) в выражениях узлов. Если переменная в момент интерпретации не определена, будет `UnknownVariableException`.

### Контекстные переменные

Пишутся с `$` внутри интерполяции (`${$имя}`) - это обычные [контекстные переменные](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Выражения.md#контекстная-переменная) LOQI. `its_QuestionGen` подкладывает их в зависимости от того, какой ключ интерпретируется:

| Переменная      | Где доступна | Что содержит |
| --------------- | ------------ | ------------ |
| `$branchResult` | `description`, `nextStepBranchResult` (у узлов агрегации, ветвей мысли и переходов) | Значение перечисления `BranchResult` - результат, о котором сейчас идёт речь: `BranchResult:CORRECT`, `BranchResult:ERROR`, `BranchResult:NULL`. |
| `$checked`      | `explanation` у [категорий ошибок поиска](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Способы%20описания/LOQI2.md#категории-ошибок-поиска) | Объект, который выбрал учащийся. |

В остальных ключах контекстных переменных нет, и обращение к ним приведёт к ошибке.

> [!important]
> `$branchResult` пригоден только для **сравнения**, но не для вывода: перечисление `BranchResult` не объявлено в модели предметной области, поэтому попытка напечатать `${$branchResult}` завершится `UnknownDomainDefinitionException`.
>
> ```groovy
> // так - правильно
> RU.description = "${X} ${$branchResult == BranchResult:CORRECT ? '' : 'не'} может выполниться следующим";
> ```
>
> Впрочем, для большинства случаев ветвление вообще не нужно: у ключей `description` и `nextStepBranchResult` есть **уточнённые варианты** `description_correct` / `description_error` / `description_null`, которые ищутся раньше общего ключа. Три отдельные строки читаются лучше, чем одна с тернарным оператором.

### Всё остальное из модели предметной области

Внутри интерполяции доступен весь язык выражений: свойства (`X.state`), связи (`X->hasOperand`), проверка класса (`X is class:Operator`), сравнения, `and`/`or`/`not`, тернарный оператор, поиск и кванторы, обращения к объектам (`obj:someObj`), классам (`class:Operator`) и значениям перечислений (`State:evaluated`).

```groovy
RU.explanation = "${X.state == State:evaluated ? 'Этот операнд уже вычислен' : 'Этот операнд ещё не вычислен'}";
```

> [!note]
> Выражения в шаблонах **не проходят валидацию** вместе с моделью - они разбираются и вычисляются в момент показа текста учащемуся. Опечатка в имени свойства приведет к ошибке времени выполнения, а не при валидации.

## Как значение превращается в текст

Результат выражения приводится к строке в соответствии с кодом локализации (`ValueToAnswerString.toLocalizedString`):

| Тип значения        | Во что превращается |
| ------------------- | ------------------- |
| объект              | метаданное `localizedName` **объекта** в нужной локализации |
| класс               | метаданное `localizedName` **класса** |
| значение перечисления | метаданное `localizedName` **значения перечисления** |
| булево              | локализованные «Да» / «Нет» |
| целое, дробное      | обычная запись числа |
| строка              | как есть |

Отсюда следует главное практическое требование:

> [!important]
> **Всё, что может попасть в текст, должно иметь `localizedName`.** Это касается объектов ситуационной модели, классов и значений перечислений - в каждой поддерживаемой локализации.
>
> Отсутствующий `localizedName` **не вызывает ошибку**: в текст просто подставляется строка `null`. Если учащийся видит «Операнд null ещё не вычислен» - ищите пропущенный `localizedName`.

Специальный случай - значения перечисления `Comparison` (`Greater`, `Less`, `Equal`): для них берутся системные локализованные строки («больше», «меньше», «равно»), собственный `localizedName` не нужен.

В `localizedName` допустима HTML-разметка - тексты доходят до учащегося как HTML:

```groovy
obj plus: Operator {
    ...
} [
    RU.localizedName = "оператор <code>+</code> на позиции 2";
    EN.localizedName = "operator <code>+</code> at position 2";
]
```

## Постобработка результата

После подстановки всех интерполяций строка проходит две обработки:

1. **Схлопывание пробелов.** Любая последовательность пробельных символов (включая переводы строк) заменяется одним пробелом. Благодаря этому длинный шаблон можно спокойно разбивать на несколько строк в исходнике, а условные вставки вида `${... ? '' : 'не'}` не оставляют двойных пробелов.
2. **LLM-«причёсывание».** Для формулировок верхнего уровня, если включён `GigaChatAPI` (`GigaChatAPI.isActive`), готовый текст дополнительно отправляется в LLM с просьбой исправить грамматику, орфографию и пунктуацию. По умолчанию выключено; при ошибке запроса возвращается исходный текст.
