Результатом работы рассуждателя является не только итоговый ответ ("верно"/"ошибка"/"неопределено"), но и **трасса** - подробная запись того, как этот ответ был получен: какие узлы графа были пройдены, в каком порядке, с какими ответами, и какие значения имели переменные на каждом шаге.

Трасса нужна как минимум для трех разных задач, и это стоит держать в голове, потому что от задачи зависит, какой вид трассы использовать:

- **работа системы.** Сторонние проекты (в первую очередь [наводящие вопросы](../3.%20Наводящие%20вопросы%20(its_QuestionGen)/Об%20its_QuestionGen.md) и сама CompPrehension) разбирают трассу, чтобы понять, какие навыки были задействованы, где учащийся ошибся и о чем его спрашивать дальше;
- **отладка графа.** Разработчик смотрит, куда пошло решение и почему, - в том числе когда решение пошло не туда;
- **автоматический анализ.** Скрипты и инструменты могут обрабатывать трассу в машиночитаемом виде.

В `its_Reasoner` есть два независимых вида трасс: **трасса графа** (по узлам) и **трасса выражений** (по шагам вычисления одного выражения). Ниже описаны оба, а также то, что происходит с трассами при аварийном завершении рассуждения.

## Трасса графа

Трасса графа представлена классом `DecisionTreeTrace` и по своей сути является **списком шагов** - объектов `DecisionTreeTraceElement`. Каждый шаг соответствует выполнению одного узла в ветви мысли и содержит:

- `DecisionTreeTraceElement.node` - **узел**, который был выполнен;
- `DecisionTreeTraceElement.nodeResult` - **результат выполнения узла**. Для [связующих узлов](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Узлы.md#Связующие%20узлы%20и%20переходы%20между%20узлами) это ответ на узел (то есть ключ совершенного перехода), для узлов результата - результат ветви `BranchResult`. У узлов агрегации ответ и результат совпадают;
- `DecisionTreeTraceElement.variablesSnapshot` - **снимок состояния переменных** на момент *завершения* данного шага.

Одна трасса соответствует одной [ветви мысли](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Узлы.md#Ветви%20мысли,%20ThoughtBranch). Трасса не может быть пустой, и её последний шаг всегда завершает ветвь.

### Результат трассы

Итоговый результат ветви определяется не последним шагом, а **результирующим** (`DecisionTreeTrace.resultingElement`). В большинстве случаев это одно и то же, но есть исключение: если предпоследний шаг совпадает с последним по результату, результирующим считается **предпоследний**.

Так сделано ради ситуации, когда после узла агрегации идет узел результата с дополнительным действием: содержательно результат определил именно узел агрегации, и именно он должен считаться "виновником" ответа, а узел результата лишь выполнил побочное действие.

От результирующего шага производны три наиболее востребованных свойства трассы:

- `DecisionTreeTrace.branchResult` - итоговый результат ветви;
- `DecisionTreeTrace.resultingNode` - узел, определивший результат;
- `DecisionTreeTrace.finalVariableSnapshot` - состояние переменных на момент определения результата.

### Вложенные трассы

Граф не линеен: узлы агрегации выполняют вложенные ветви мысли, цикл `while` выполняет свое тело многократно, а [субинтерпретатор](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Субинтерпретаторы.md) выполняет вообще другой граф. Поэтому трасса **древовидна**: некоторые шаги содержат вложенные трассы (`DecisionTreeTraceElement.nestedTraces()`).

| Вид шага                                       | Чему соответствует                       | Что вложено                                                                   |
| ---------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------ |
| `LinkDecisionTreeTraceElement`                 | обычный связующий узел (вопрос, действие) | ничего                                                                        |
| `BranchResultDecisionTreeTraceElement`         | узел результата                           | ничего                                                                        |
| `AggregationDecisionTreeTraceElement`          | узел агрегации по ветвям или цикл по объектам | мапа "ветвь агрегации → её трасса". Для цикла по объектам ключом является объект итерации |
| `WhileCycleDecisionTreeTraceElement`           | цикл `while`                              | список трасс - по одной на каждую итерацию тела                                |
| `RedirectedBranchResultDecisionTreeTraceElement` | узел перенаправления результата           | трасса вызванного субинтерпретатора                                            |

Благодаря этому по трассе можно проверить, выполнялся ли конкретный узел, - как в самой ветви (`containsNode`), так и с учетом всех вложенных (`containsWithNested`).

### Исключительные результаты в трассе

Узлы результата, помеченные как [исключительные ситуации](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Соглашения%20о%20метаданных.md#исключительные-ситуации), собираются из трассы отдельно - методом `DecisionTreeTrace.branchResultExceptions()`. Он проходит и по вложенным трассам тоже, поэтому находит в том числе аварийные завершения внутри циклов, агрегаций и субинтерпретаторов.

Каждый такой результат представлен объектом `BranchResultException` с полями `result`, `exceptionName` и `nodeId`. Отдельно доступен `resultingBranchResultException()` - исключительный результат, которым завершилась сама ветвь (если он есть).

Обратите внимание, что это **не исключения JVM**: рассуждение при их появлении не прерывается, они лишь помечаются в трассе. Единственное место, где такой результат превращается в настоящее исключение, - вызов субинтерпретатора: там аварийное завершение вложенного графа выбрасывает `SubinterpreterException`.

## Трасса выражений

Трасса выражений (`ExpressionTrace`) отвечает на вопрос "почему это выражение вернуло именно это значение". В отличие от трассы графа, она **древовидна по построению**: каждый узел трассы соответствует одному подвыражению и содержит:

- `ExpressionTrace.expression` - само подвыражение;
- `ExpressionTrace.value` - его значение;
- `ExpressionTrace.isValueAnnotated` - было ли значение вообще вычислено (некоторые подвыражения не вычисляются - например, правый операнд `and` при ложном левом);
- `ExpressionTrace.children` - трассы вложенных подвыражений;
- `ExpressionTrace.iterationObject` - объект итерации, если данный шаг является перебором объекта в операторе поиска или в кванторе.

### Компактная запись переборов

Операторы поиска и кванторы перебирают объекты, и наивная запись такого перебора мгновенно раздувает трассу до нечитаемого объема. Поэтому переборы записываются компактно:

```
1. find Operand x { $x=>isOperandOf(Y) } => Obj(operand_1)
    iterations: 1 matched / 14 checked
      + [Obj(operand_1)] => true
      - 13 not matched
```

Правила сокращения следующие:

- сначала выводится сводка "сколько подошло из скольких проверенных";
- подошедшие объекты (`+`) и объекты с неопределенным результатом (`?`) выводятся всегда;
- неподошедшие (`-`) сворачиваются в одну строку "N not matched", **если** ни у одного из них нет детализации. Если же детализация есть, они выводятся по отдельности - именно этот случай обычно и интересен при отладке;
- кроме того, при сборе трассы неподошедшие итерации перестают записываться после 32 штук - иначе перебор по большой модели съедал бы память.

### Как получить трассу выражения

Сбор трассы выражений заметно дороже обычного вычисления, поэтому по умолчанию он выключен. Включить его можно тремя способами:

- **на всё рассуждение** - опцией `ReasoningOptions.collectExpressionTrace` (в [CLI](../4.%20Инструменты/CLI.md) это делает флаг `--debug`). Тогда трасса выражения сохранится, если рассуждение упадет;
- **точечно, внутри графа** - [отладочным вызовом](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Способы%20описания/LOQI2.md#отладочные-вызовы) `debug:trace(выражение)`. Он вычисляет переданное выражение, печатает его трассу и возвращает значение, поэтому его можно "обернуть" вокруг любого подозрительного выражения прямо в графе;
- **при запросе к модели** - опцией `--trace` команды `reasoner-cli expression-query`.

## Трассы при аварийном завершении

Если рассуждение завершилось исключением, обычной трассы не будет: она не была достроена, а `DecisionTreeTrace` по контракту обязана завершаться результатом. Для таких случаев существует **частичная трасса** (`PartialDecisionTreeTrace`), которая:

- не требует завершающего результата - это просто список уже пройденных шагов;
- дополнительно хранит `failedNode` - узел, на котором рассуждение сломалось;
- хранит `variableSnapshot` - состояние переменных на момент падения.

Частичная трасса, вместе с трассой выражения, прикрепляется к исключению `ReasoningException` (поля `partialDecisionTreeTrace` и `expressionTrace`) и "поднимается" вместе с ним по стеку. Даже если исходное исключение не было `ReasoningException`, оно оборачивается в него - чтобы трасса не потерялась.

Сбор частичных трасс включается опцией `ReasoningOptions.collectPartialTrace`; в CLI - тем же флагом `--debug`.

Отдельно стоит отметить, что состояние переменных на момент падения печатается CLI **всегда**, независимо от режима отладки: в подавляющем большинстве случаев именно оно объясняет причину падения.

## Ограничение времени рассуждения

Некорректно написанный граф может зациклиться - например, если условие цикла `while` никогда не перестает выполняться. Чтобы такое не подвешивало вызывающий код, рассуждение можно ограничить по времени:

```java
ReasoningOptions options = new ReasoningOptions(
    ReasoningControl.withTimeLimitSeconds(10),
    /* collectExpressionTrace = */ false,
    /* collectPartialTrace = */ true
);
DecisionTreeTrace trace = DecisionTreeReasoner.solve(decisionTree, situation, options);
```

Механизм устроен как расстановка **контрольных точек**: рассуждатель периодически проверяет, не истек ли срок и не был ли прерван поток. Проверка выполняется не на каждом шаге, а раз в несколько тысяч контрольных точек - чтобы сама проверка не стала заметной статьей расходов.

По истечении срока выбрасывается `ReasoningTimeoutException` с указанием лимита и, по возможности, места, где рассуждение находилось в этот момент. Прерывание потока приводит к `ReasoningInterruptedException`.

В [CLI](../4.%20Инструменты/CLI.md) ограничение задается опцией `--time-limit SECONDS` (поддерживается и в `reason`, и в `expression-query`).

## Форматы вывода

### Человекочитаемый

Основной формат для отладки. Трасса графа печатается как нумерованный список шагов с отступами для вложенных трасс:

```
Result: CORRECT
Variables:
  X = Obj(operand_1)
  Y = Obj(operator_1)
Trace:
  1. QuestionNode [id=isEvaluated, line=42] => false
  2. FindActionNode [id=findOperand, line=51] => true
  3. CycleAggregationNode [id=checkAll] => CORRECT
    branch[0]: Obj(operand_1)
       1. QuestionNode [id=operandState] => true
       2. BranchResultNode [id=operandOk, skill=operand_order] => CORRECT
    branch[1]: Obj(operand_2)
       ...
  4. BranchResultNode [id=allEvaluated, skill=operand_order] => CORRECT
```

В квадратных скобках выводятся метаданные узла: `id` и `line`, а для узлов результата дополнительно `skill` и `exceptionName`/`exception`. Вложенные трассы подписываются по своему виду: `branch[N]` для агрегаций, `iteration[N]` для цикла `while`, `redirected:` для субинтерпретатора.

Подробный режим (`verbose`) добавляет LOQI-запись выражения для узлов, у которых не задан `id`, - то есть ровно там, где узел иначе невозможно опознать.

### JSON

Машиночитаемый формат, используемый в JSONL-выводе CLI и в [JSON-RPC сервере](../4.%20Инструменты/JSON-RPC%20сервер.md). Трасса сериализуется в объект с полями `branchResult`, `finalVariables` и `elements`, где каждый элемент содержит:

- `nodeType` - имя класса узла;
- `nodeId` - значение метаданного `id`;
- `nodeResult` - результат шага;
- `variables` - снимок переменных;
- `metadata` - все метаданные узла в виде списка `{name, locCode, value}`;
- для агрегаций дополнительно `aggregationMethod` и `branches`, для цикла `while` - `iterations`, для перенаправления результата - `redirectedTrace`.

Переменные сериализуются не просто именем, а объектом с полями `repr_name`, `object_name`, `type` и `metadata` - чтобы потребителю не приходилось дополнительно запрашивать модель, чтобы понять, что это за объект.

Трасса выражений в JSON устроена аналогично: `expression` (в LOQI-записи), `value`, `isValueAnnotated`, `children`, и `iterationObject` для шагов перебора.

> [!note]
> В JSONL-выводе CLI трасса по умолчанию передается как **уже отформатированная строка** в поле `value`. Структурированный JSON включается флагом `--json-trace` - он объемнее, но пригоден для программного разбора. Подробнее о событиях JSONL см. [[../4. Инструменты/CLI.md#машиночитаемый-вывод-jsonl|страницу про CLI]].

## Получение трассы в коде

```java
DomainSolvingModel model = ... ;
LearningSituation situation = ... ;

// простейший вариант - без трасс выражений и ограничений по времени
DecisionTreeTrace trace = DecisionTreeReasoner.solve(model.getDecisionTree(), situation);

System.out.println(trace.getBranchResult());
System.out.println(trace.getResultingNode());
System.out.println(trace.getFinalVariableSnapshot());
```

Форматирование трасс доступно как набор функций в `its.reasoner.utils`: `formatDecisionTreeTrace`, `formatPartialDecisionTreeTrace`, `formatExpressionTraces` - человекочитаемый вид, и `toJsonValue` - структурированный.

Отдельно стоит помнить, что **отладочные процедуры печатают не через `System.out` напрямую**, а через `ReasonerOutput`. Это позволяет перехватить их вывод - именно так CLI в JSONL-режиме превращает сообщения `debug:print` и `debug:dump` в события `reasoner-output`, а не смешивает их с остальным выводом:

```java
ReasonerOutput.withSink(
    message -> log.debug(message),
    () -> DecisionTreeReasoner.solve(decisionTree, situation)
);
```
