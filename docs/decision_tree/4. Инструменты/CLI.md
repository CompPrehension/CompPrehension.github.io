Проекты [its_DomainModel](../1.%20Модели%20(its_DomainModel)/Об%20its_DomainModel.md) и [its_Reasoner](../2.%20Вычисления%20(its_Reasoner)/Об%20its_Reasoner.md) помимо библиотечного API предоставляют **интерфейс командной строки**. Он нужен для типовых операций, которые разработчик домена выполняет постоянно: валидация модели, преобразование графа между представлениями, запуск рассуждателя на конкретной ситуации и анализ полученной трассы.

Обе утилиты построены на библиотеке [picocli](https://picocli.info/), устроены одинаково (общая команда + подкоманды) и поддерживают стандартные флаги `--help` и `--version`.

## Сборка и запуск

Каждый проект собирается дополнительно в особый jar (с суффиксом `all`), содержащий все зависимости, и самодостаточный для запуска как одиночный файл:

```bash
mvn -DskipTests package
java -jar target/its_DomainModel-<версия>-all.jar <подкоманда> [аргументы]
java -jar target/its_Reasoner-<версия>-all.jar <подкоманда> [аргументы]
```

Далее в примерах для краткости используются имена команд `domain-cli` и `reasoner-cli`.

> [!note]
> В Windows-консоли CLI отдельно настраивает кодировку вывода под кодировку консоли, чтобы русскоязычные сообщения не превращались в "кракозябры". Эта настройка отключается при выводе в формате `jsonl` (см. [ниже](#машиночитаемый-вывод-jsonl)).

## its_DomainModel: `domain-cli`

| Подкоманда             | Назначение                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| `validate-dsm`         | Проверяет `DomainSolvingModel` целиком - директорию с моделью, тегами и графами                          |
| `validate-domain-loqi` | Проверяет отдельный domain-LOQI файл, объединенный с базовой моделью (и, возможно, тегом)                |
| `tree-loqi-to-xml`     | Преобразует граф из [LOQI2](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Способы%20описания/LOQI2.md) в XML |
| `decompile-tree`       | Обратное преобразование: XML → LOQI2/TPG (**экспериментально**)                                          |
| `discover-tree`        | Ищет узлы графа по метаданным                                                                            |
| `dict-to-loqi`         | Собирает домен из [старых CSV-словарей и `domain.ttl`](../1.%20Модели%20(its_DomainModel)/Модель%20предметной%20области/Представления%20данных/Словари%20+%20RDF.md) и сохраняет его в LOQI |
| `domain-to-rdf`        | Записывает конкретный домен в RDF Turtle                                                                 |
| `rdf-to-domain-loqi`   | Наполняет домен данными из RDF TTL и сохраняет результат в LOQI                                          |

### Валидация модели

```bash
domain-cli validate-dsm ./domain
domain-cli validate-dsm ./domain --build-method DICT_RDF
domain-cli validate-dsm ./domain --debug
```

Команда строит `DomainSolvingModel` из указанной директории (файлы `domain.loqi`, `tag_*.loqi`, графы `tree*.xml`/`tree*.loqi`/`*.tpg`) и полностью её валидирует - включая все графы.

Флаг `--debug` описан [ниже](#режим-отладки---debug).

### Преобразование графа

```bash
domain-cli tree-loqi-to-xml tpg_main.tpg -o tree_main.xml
domain-cli tree-loqi-to-xml tpg_main.tpg --model-dir ./domain --tag expression
```

Если указана `--model-dir` (и, опционально, `--tag`), то граф не просто преобразуется, а еще и валидируется относительно соответствующей модели предметной области - это основной способ убедиться, что выражения в графе корректны.

Флаг `--cdata-expressions` записывает выражения в XML в виде CDATA с LOQI-представлением, что делает получившийся XML заметно читаемее.

Обратное преобразование:

```bash
domain-cli decompile-tree tree_main.xml -o tpg_main.tpg --tree-name MyGraph
```

Оно является **экспериментальным** (о чем команда предупреждает в потоке `stderr`) и предназначено в первую очередь для анализа и миграции существующих графов.

### Поиск узлов по метаданным

По мере роста графа найти в нем нужный узел становится нетривиальной задачей - особенно если граф собирается из [фрагментов](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Способы%20описания/LOQI2.md#фрагменты) и содержит сотни узлов. Команда `discover-tree` решает эту задачу через [метаданные](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Соглашения%20о%20метаданных.md):

```bash
# найти узел по идентификатору
domain-cli discover-tree tpg_main.tpg -m id=noOperandsFound

# найти все узлы, связанные с конкретным навыком, и показать их дочерние узлы
domain-cli discover-tree tpg_main.tpg -m skill=unevaluated_operand --children

# найти узел, собранный из конкретной строки исходника
domain-cli discover-tree tpg_main.tpg -m line=128
```

Особенности:

- критериев `-m KEY=VALUE` можно указать несколько; по умолчанию они объединяются через **И**, флаг `--union` меняет это на **ИЛИ**;
- работает как с LOQI2/TPG, так и с XML-представлением графа;
- если среди критериев есть `line`, граф автоматически строится с отладочными метаданными - иначе искать по номеру строки было бы нечем;
- `--children` дополнительно выводит сводку о непосредственных дочерних узлах: их общее количество и дескрипторы тех из них, у которых задан `id`, `line` или `skill`;
- `--limit` ограничивает количество выводимых узлов, `--format jsonl` переключает вывод в машиночитаемый формат.

## its_Reasoner: `reasoner-cli`

| Подкоманда                       | Назначение                                                                     |
| -------------------------------- | -------------------------------------------------------------------------------- |
| `reason`                         | Запускает рассуждение по графу на конкретной учебной ситуации                     |
| `expression-query` (`expr-query`) | Вычисляет произвольное LOQI-выражение на домене и печатает найденные объекты      |

### Запуск рассуждения

```bash
reasoner-cli reason ./domain situation.loqi
reasoner-cli reason ./domain situation.loqi --tag expression --tree checkOperands
```

Команда объединяет базовую модель из директории (с учетом `--tag`) с моделью конкретной ситуации из указанного LOQI-файла, валидирует результат и запускает рассуждатель по выбранному графу (`--tree`; по умолчанию используется граф без имени).

Полезные опции:

- `--verbose` - подробная трасса, включая LOQI-представление выражений в узлах;
- `--no-trace` - вывести только результат и итоговые переменные, без трассы;
- `--time-measure` - измерить и вывести время подготовки модели и время рассуждения;
- `--time-limit SECONDS` - прервать рассуждение по истечении заданного времени (защита от зацикливания графа);
- `-o, --export-domain FILE` - сохранить итоговую модель ситуации (за вычетом базовой модели) в LOQI. Это удобно, чтобы увидеть, как рассуждение изменило ситуацию - какие объекты были созданы, какие связи добавлены или удалены.

### Запросы к модели выражением

```bash
reasoner-cli expr-query situation.loqi 'find Operand x { $x=>isOperandOf(Y) }'
reasoner-cli expr-query ./domain situation.loqi 'find Operand x { ... }' --trace --loqi
```

Команда вычисляет [выражение](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Выражения.md) на модели и печатает имена найденных объектов. Директорию модели можно не указывать, если LOQI-файл самодостаточен.

Опция `--loqi` дополнительно печатает для каждого найденного объекта его полное LOQI-объявление (`obj name : Class { ... }`), `--limit` ограничивает количество объектов, `--trace` включает трассу вычисления выражения.

Эта команда - основной способ быстро проверить гипотезу "а что вернет вот такое выражение на этой ситуации" до того, как встраивать его в граф.

## Трасса и её анализ

Главный результат работы `reasoner-cli reason` - **трасса рассуждения**.

> [!tip]
> Здесь описано только то, как трасса выглядит в выводе CLI и какими опциями управляется. О том, как трасса устроена, что такое частичные трассы и трассы выражений, читайте в отдельной статье: [[../2. Вычисления (its_Reasoner)/Трассы рассуждения.md|Трассы рассуждения]].

По умолчанию трасса печатается в человекочитаемом виде:

```
Result: CORRECT
Variables:
  X = Obj(operand_1)
  Y = Obj(operator_1)
Trace:
  1. QuestionNode [id=isEvaluated, line=42] => false
  2. FindActionNode [id=findOperand, line=51] => true
  3. CycleAggregationNode [id=checkAll] => CORRECT
    ...
  4. BranchResultNode [id=allEvaluated, skill=operand_order] => CORRECT
```

В квадратных скобках выводятся метаданные узла: `id`, `line`, а для узлов результата дополнительно `skill` и, если узел помечен как [исключительная ситуация](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Соглашения%20о%20метаданных.md#исключительные-ситуации), - `exceptionName`. Именно поэтому соглашение задавать узлам `id` так важно: без него трасса перестает быть соотносимой с исходным графом.

Если в трассе встретились исключительные результаты, они дополнительно перечисляются отдельным блоком:

```
Exceptions:
  - id=noOperandsFound; result=ERROR; exceptionName=NoOperandsFound
```

## Режим отладки (`--debug`)

Флаг `--debug` поддерживается теми подкомандами, которые строят модель целиком (`validate-dsm`, `discover-tree`, `reason`, `expression-query`), и означает несколько связанных вещей:

1. **Разрешает отладочные вызовы.** По умолчанию валидация модели падает, если в графе остались [вызовы процедур из пространства `debug`](../1.%20Модели%20(its_DomainModel)/Дерево%20решений/Способы%20описания/LOQI2.md#отладочные-вызовы). Это защита от того, чтобы отладочный код случайно уехал в production-граф. С `--debug` эта проверка отключается;
2. **Включает отладочные метаданные.** Граф строится с метаданными `line`, поэтому в трассе рядом с узлами появляются номера строк исходного LOQI2-файла;
3. **Включает сбор частичных трасс** (в `reason`) - трассы графа и трассы выражения при падении рассуждения.

Типичный цикл отладки графа выглядит так:

```bash
# 1. Проверяем, что граф собирается и валиден (с отладочными вызовами внутри)
domain-cli validate-dsm ./domain --debug

# 2. Прогоняем рассуждение с подробной трассой
reasoner-cli reason ./domain situation.loqi --debug --verbose

# 3. Нашли подозрительный номер строки в трассе - смотрим, что это за узел
domain-cli discover-tree ./domain/tpg_main.tpg -m line=128 --children

# 4. Перед сдачей работы убеждаемся, что отладочного кода не осталось
domain-cli validate-dsm ./domain
```

## Машиночитаемый вывод (`jsonl`)

Обе утилиты поддерживают `--format jsonl` - вывод в формате [JSON Lines](https://jsonlines.org/), где каждая строка является отдельным JSON-объектом с полем `type`. Формат предназначен для анализа сторонними инструментами и скриптами.

`reasoner-cli reason` выдает следующие события: `result` (итоговый результат), `final-node` (итоговый узел), `variables` (итоговые переменные), `exceptions` (исключительные результаты), `trace` (трасса), `metric` (замеры времени), `reasoner-output` (вывод отладочных процедур), `artifact`/`service` (экспорт итогового домена). При падении добавляются `partial-trace` и `partial-expression-trace`, а также объект ошибки.

По умолчанию трасса выводится в поле `value` как уже отформатированная строка. Флаг `--json-trace` заставляет выводить её как структурированный JSON - это удобнее для программного разбора, но объемнее.

`domain-cli discover-tree` в этом формате выдает событие `summary` (сколько узлов найдено и сколько показано) и по одному событию `node` на каждый найденный узел.

> [!tip]
> Если те же операции нужно выполнять часто и подряд, стоит посмотреть на [JSON-RPC сервер](./JSON-RPC%20сервер.md): он предоставляет ровно те же операции, но без затрат на запуск JVM при каждом вызове.
