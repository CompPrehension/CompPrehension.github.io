> [!warning] Для разработчиков проектов, использующих TPG

**compph-toolchain-server** - долгоживущий HTTP-сервер, предоставляющий инструментарий CompPrehension по протоколу [JSON-RPC 2.0](https://www.jsonrpc.org/specification). Он поднимает JVM один раз и вызывает библиотеки `its_*` напрямую, в своем же процессе.

Репозиторий: [github.com/CompPrehension/CompPrehension-Toolchain-Server](https://github.com/CompPrehension/CompPrehension-Toolchain-Server)

## Зачем это нужно

Каждый инструмент поставляется как [CLI](./CLI.md) - исполняемый jar. Это удобно для разовых запусков, но при разработке домена одни и те же операции выполняются **многократно и подряд**: провалидировать модель, перевести фрагмент кода, прогнать рассуждатель, снова провалидировать.

Проблема в том, что на каждый такой вызов приходится запускать новую JVM. Основное время при этом уходит не на саму работу, а на старт виртуальной машины и загрузку классов - и это накладные расходы, которые никак не связаны с полезной нагрузкой. Особенно заметно это становится в автоматизированных сценариях: в скриптах, в тестовых прогонах, при работе через LLM-агентов, которые вызывают инструменты десятками раз за сессию.

Сервер решает эту задачу прямолинейно: JVM стартует один раз, все инструменты подключены как обычные Maven-зависимости и вызываются как библиотеки. Запросы приходят по HTTP и обрабатываются сразу, без порождения процессов. Дополнительно это дает:

- **параллельность** - независимые запросы обрабатываются одновременно;
- **структурированный ответ** - там, где CLI печатал человекочитаемый текст, сервер возвращает JSON. Модель событий JSONL из `its_Reasoner` при этом переиспользуется как есть;
- **работу с удаленной машины** - сервер можно поднять не только локально.

## Устройство

Сервер написан на Kotlin с использованием [Javalin](https://javalin.io) и Jackson, собирается в единый исполняемый jar.

Каждому инструменту соответствует свой маршрут, на котором размещен набор JSON-RPC методов, повторяющих подкоманды соответствующего CLI:

| Инструмент      | Маршрут              | Что делает                                                                                     |
| --------------- | -------------------- | ------------------------------------------------------------------------------------------------ |
| its_DomainModel | `POST /rpc/domain`   | Валидация и преобразование моделей предметной области и графов (LOQI / XML / RDF / CSV-словари)   |
| its_Reasoner    | `POST /rpc/reasoner` | Рассуждение по графу и вычисление LOQI-выражений                                                  |

Немногочисленные операции инструментов, которые обращаются к изменяемому глобальному состоянию процесса, защищены отдельными узкими блокировками.

### Запуск

```bash
mvn -DskipTests package
java -jar target/compph-toolchain-server-<версия>.jar [ПОРТ]
```

Настройки берутся из переменных окружения и/или файла `.env` в рабочей директории:

| Настройка              | Источник                        | По умолчанию |
| ---------------------- | ------------------------------- | ------------- |
| Порт                   | первый аргумент или `PORT`      | `8080`        |
| Адрес прослушивания    | `HOST`                          | `0.0.0.0`     |
| Секрет доступа         | `ACCESS_SECRET`                 | *(отключен)*  |

Для сборки нужны артефакты инструментов - либо установленные локально (`mvn install` в каждом проекте), либо подтянутые через [jitpack.io](https://jitpack.io); конкретные версии закреплены в `pom.xml` сервера.

### Аутентификация

Если задан непустой `ACCESS_SECRET`, то каждый запрос к RPC-маршрутам должен предъявить этот секрет - заголовком `X-Access-Secret`, заголовком `Authorization: Bearer <secret>` или параметром запроса `access_secret`. Иначе сервер отвечает `HTTP 403`. Если секрет не задан, доступ открыт.

Документационные и служебные эндпоинты (`/`, `/health`, `/{маршрут}/docs`, `/{маршрут}/openrpc.json`) доступны всегда.

## Документация методов

Одна из идей сервера - документация, которая не может разойтись с реализацией. Для каждого маршрута из того же реестра методов, по которому происходит диспетчеризация запросов, генерируется документ [OpenRPC](https://open-rpc.org) (аналог OpenAPI/Swagger для JSON-RPC), а также самодостаточная HTML-страница:

| Эндпоинт                      | Содержимое                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------- |
| `GET /`                       | HTML-индекс всех маршрутов и соглашений о формате запросов                       |
| `GET /health`                 | Проба живости и самоописание: имя сервера, версия, список доступных инструментов |
| `GET /{маршрут}/docs`         | HTML-документация одного инструмента                                             |
| `GET /{маршрут}/openrpc.json` | Машиночитаемый OpenRPC-документ одного инструмента                               |

Соответственно, **актуальный список параметров каждого метода следует смотреть именно там**, а не в этой статье.

## Формат запросов

Запрос - это обычный объект JSON-RPC 2.0 (или массив таких объектов - batch). Запросы без `id` считаются уведомлениями и остаются без ответа (если тело состоит только из них, сервер отвечает `HTTP 204`).

```json
{ "jsonrpc": "2.0", "id": 1, "method": "validate-dsm", "params": { } }
```

Тело можно отправить двумя способами:

- `application/json` - тело является JSON-RPC запросом; содержимое файлов передается прямо в нем (текстом или base64);
- `multipart/form-data` - поле формы `request` содержит JSON-RPC запрос, а остальные части формы являются загружаемыми файлами, на которые запрос ссылается по имени. Это эффективный способ передать большие файлы без накладных расходов на base64.

### Имитированные файлы и директории

Инструменты `its_*` работают с файлами и директориями (модель домена - это директория с определенным набором файлов). Поэтому методы, которым нужны файлы, принимают **имитированные** файловые аргументы: сервер материализует их во временную директорию на время обработки запроса, а затем удаляет.

Файл (`FileSource`) может быть задан одним из способов:

```jsonc
"текст прямо строкой"
{ "text": "текст" }
{ "base64": "<байты в base64>" }
{ "ref": "<имя части multipart-формы>" }
```

Директория (`DirSource`) - одним из:

```jsonc
{ "files": { "domain.loqi": <FileSource>, "tpg_main.tpg": <FileSource> } }
{ "ref": "<имя части multipart-формы с zip-архивом>" }
```

Имена файлов внутри такой директории должны соответствовать тому, что ищут инструменты: `domain.loqi` и `tag_<имя>.loqi` для модели; `tree.xml` / `tree_<имя>.xml` / `tpg_<имя>.xml`, их `.loqi`-аналоги и `<имя>.tpg` для графов; `enums.csv`, `classes.csv`, `properties.csv`, `relationships.csv`, `domain.ttl` для сборки из словарей. Лишние файлы можно передавать - они просто не будут прочитаны.

## Доступные методы

### `/rpc/domain` (its_DomainModel)

| Метод                  | Назначение                                                                 |
| ---------------------- | ---------------------------------------------------------------------------- |
| `validate-dsm`         | Проверить директорию `DomainSolvingModel`                                     |
| `tree-loqi-to-xml`     | Преобразовать граф LOQI2 → XML (с опциональной валидацией на модели)          |
| `decompile-tree`       | Декомпилировать граф XML → LOQI2/TPG (экспериментально)                        |
| `discover-tree`        | Найти узлы графа по метаданным                                                |
| `dict-to-loqi`         | Собрать домен из CSV-словарей и `domain.ttl`, выдать LOQI                      |
| `validate-domain-loqi` | Проверить дополнительный domain-LOQI, объединенный с моделью                   |
| `domain-to-rdf`        | Собрать конкретный домен и записать его в RDF Turtle                           |
| `rdf-to-domain-loqi`   | Наполнить конкретный домен из RDF TTL и выдать LOQI                            |

### `/rpc/reasoner` (its_Reasoner)

| Метод              | Назначение                                                                          |
| ------------------ | ------------------------------------------------------------------------------------- |
| `reason`           | Запустить рассуждение по графу; возвращает результат, переменные, исключения, трассу и метрики |
| `expression-query` | Вычислить LOQI-выражение и вернуть найденные объекты                                   |

## Поддержка MCP

Помимо JSON-RPC, сервер поддерживает [Model Context Protocol](https://modelcontextprotocol.io) на едином эндпоинте `POST /mcp` (транспорт Streamable HTTP). Это сделано для того, чтобы инструментарий можно было напрямую подключать к LLM-агентам - как раз к тому сценарию, где накладные расходы на запуск JVM особенно болезненны.

Каждый RPC-метод автоматически становится MCP-инструментом с именем `<модуль>__<метод>` - например, `domain__validate-dsm`, `reasoner__reason`. Список инструментов и схемы их входа/выхода порождаются из того же реестра методов, поэтому любой новый метод появляется в MCP автоматически.

Поддерживаются методы `initialize`, `tools/list`, `tools/call`, `ping`. Эндпоинт не хранит состояние (нет идентификатора сессии и серверных SSE-событий) и защищается тем же `ACCESS_SECRET`. Файловые аргументы используют то же соглашение `FileSource`/`DirSource`, за исключением варианта `ref` (доступны `text`, `base64`, `path`).

## Ошибки

Ошибки возвращаются по правилам JSON-RPC 2.0. Помимо стандартных кодов (`-32700` разбор, `-32600` некорректный запрос, `-32601` метод не найден, `-32602` некорректные параметры, `-32603` внутренняя ошибка) используются:

- `-32000` - инструмент выбросил исключение при обработке корректных параметров. В `error.data` передаются `exceptionName`, `rootCause`, `rootCauseMessage` и урезанный `stackTrace`;
- `-32001` - файловый или директорный аргумент не удалось разрешить или материализовать.
