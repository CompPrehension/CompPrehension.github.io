[Метаданные](../Модель%20предметной%20области/Метаданные.md) - это произвольные пары "ключ-значение", которые можно привязать к элементам модели. Сама модель их никак не интерпретирует: с точки зрения `its_DomainModel` любой ключ равноправен.

Однако на практике вокруг метаданных [графа мыслительных процессов](./Дерево%20(граф)%20решений.md) сложился набор **соглашений** - ключей, которые ожидают увидеть конкретные потребители: рассуждатель, генератор наводящих вопросов, инструменты отладки и система CompPrehension. Эта страница описывает такие ключи, их назначение и то, к каким элементам графа они применяются.

> [!important]
> Ничто из перечисленного здесь **не проверяется валидатором модели**. Отсутствие ожидаемого ключа обычно не влияет на поведение графа решений, но может привести к ошибке времени выполнения в "обвязках" вокруг интерпретатора (в случае ключей наводящих вопросов) или к менее информативному выводу (в инструментах отладки)

## Как задаются метаданные

Способ описания зависит от того, как создается граф:

- в [[./Способы описания/LOQI2.md#метаданные|LOQI2]] - блоком `[ ключ = значение; ]` или ссылкой `as ID` на блок `meta for ID [...]`;
- в сериализованном `xml` - атрибутами узла с префиксом `_` (например, `_skill="unevaluated_operator"`).

Метаданные поддерживают [локализацию](../Модель%20предметной%20области/Метаданные.md): ключ может быть записан как `RU.explanation` или `EN.explanation`. Локализованными являются в первую очередь ключи, содержащие текст на естественном языке.

## Ключи идентификации и отладки

Эти ключи используются самими `its_DomainModel` и `its_Reasoner` - для того, чтобы человек мог соотнести элемент трассы или сообщение об ошибке с конкретным местом в графе.

| Ключ    | К каким элементам применяется | Тип данных | Назначение |
| ------- | ----------------------------- | ---------- | ---------- |
| `id`    | любой узел, переход, ветвь мысли | целое положительное число | **Стабильный идентификатор элемента.** Основной способ адресовать узел графа извне. |
| `line`  | любой узел | целое положительное число | **Номер строки в исходном LOQI2-файле.** Отладочный ключ, добавляется автоматически в режиме отладки. |
| `alias`, `label` | любой элемент графа | строка | Аналогичен `id`, но является строковым псевдонимом. |

### `id`

Значение `id` попадает:

- в человекочитаемую трассу рассуждателя - `QuestionNode [id=checkEvaluated] => true`;
- в сообщения об исключениях рассуждателя;
- в вывод команды поиска узлов [`domain-cli discover-tree`](../../4.%20Инструменты/CLI.md#its_domainmodel-domain-cli).

Из этого следует главная рекомендация: **`id` стоит задавать всем узлам, за которые "цепляется" отладка** - узлам результата, ключевым вопросам, узлам агрегации. Значение должно быть уникальным в пределах графа, иначе трасса перестанет быть однозначной.

Для корректной работы сторонних инструментов `id` требуется задавать как целое число. Если требуется именно строковый псевдоним узла - используйте ключ метаданных `alias`

### `line`

`line` не описывается разработчиком вручную - он добавляется построителем графа из LOQI2, если построение запущено с включенными отладочными метаданными:

```java
DecisionTree tree = TreeLoqiBuilder.buildTree(reader, /* debugMeta = */ true);
```

В [CLI](../../4.%20Инструменты/CLI.md) за это отвечает флаг `--debug`; команда `discover-tree` включает его автоматически, если среди критериев поиска указан `line`.

Данный ключ метаданных не имеют смысла в отрыве от исходного файла в формате LOQI2. Также рекомендуется не использовать его для собственных целей, т.к. он вероятно, будет затёрт в режиме отладки.

Так как `line` привязан к тексту исходного файла, он **не должен попадать в графы, готовые к развертыванию в тренажере**: при любом редактировании исходного файла значения устаревают.

### `alias`

`alias` - это имя элемента "для человека". Он используется:

- в текстовом описании элемента (`DecisionTreeElement.description`), а значит в сообщениях валидации и трассах;
- при [[./Способы описания/LOQI2.md#экспериментальная-кодогенерация-loqi2|обратной кодогенерации LOQI2]] - как имя блока `meta for` и метка перехода `-[alias]->`;
- в `its_QuestionGen` - как ключ элемента при формировании наводящих вопросов.

> [!note]
> Псевдоним `as ID` в LOQI2 и метаданное `alias` - **это разные вещи**. `as ID` - это имя блока метаданных на уровне синтаксиса, оно не сохраняется в модели. Если элементу нужен `alias`, его надо явно записать внутри блока:
> ```groovy
> meta for evaluationAsk [
>     alias = "evaluationAsk";
>     id = "evaluationAsk";
> ]
> ```

## Ключи узлов результата

Эти ключи применяются к [[./Узлы.md#узлы-результатов-branchresultnode|узлам результата (`BranchResultNode`)]] - то есть к узлам, завершающим ветвь мысли. Именно они несут педагогический смысл графа: какая ошибка была допущена, какой навык при этом задействован.

| Ключ            | Тип данных | Значение |
| --------------- | ---------- | -------- |
| `skill`         | строка; несколько значений разделяются `;` | **Навык (умение), с которым связан данный результат.** |
| `law`           | строка; несколько значений разделяются `;` | **Правило (закон) предметной области**, применение или нарушение которого фиксирует данный результат. Считается **устаревшим** и не обязателен в новых доменах. |
| `explanation`   | локализованная строка | **Локализованное объяснение** для учащегося: почему получен такой результат. Обычно записывается как `RU.explanation` / `EN.explanation`. |
| `muted`         | логическое значение | Если равно `true`, результат не должен показываться учащемуся в агрегации ответов рассуждателя в CompPrehension. |

`skill` и `law` считываются CompPrehension при разборе трассы: по ним определяется, какие навыки были задействованы, и какие правила нарушены. Значение `skill` также выводится в трассе рассуждателя и в дескрипторах узлов команды `discover-tree`.

Значение `explanation` - **шаблон**: в него можно подставлять выражения, вычисляемые по конкретной ситуации (см. [[../../3. Наводящие вопросы (its_QuestionGen)/Шаблонизация текстов.md|«Шаблонизация текстов»]]).

Пример:

```groovy
conclude : error [
    skill = "unevaluated_operand;operand_order";
    law = "operator_evaluation_order";
    RU.explanation = "Операнд ${X} еще не вычислен";
    EN.explanation = "Operand ${X} is not evaluated yet";
];
```

### Исключительные ситуации

Отдельное соглашение - пометка узла результата как **исключительной ситуации**. Это результат, который сигнализирует не об ошибке учащегося, а о том, что граф столкнулся с ситуацией, которую не может корректно обработать (некорректные входные данные, недостижимое состояние модели и т.п.). Исключительные ситуации помогают отладить граф мыслительных процессов

| Ключ            | Тип данных | Значение |
| --------------- | ---------- | -------- |
| `exception`     | логическое значение | Если равно `true` (или `1`), данный узел результата является исключительной ситуацией. |
| `exceptionName` | строка | Опциональный короткий машиночитаемый идентификатор ситуации, выводимый в отладке. Если не задан, ситуация считается безымянной. |

Пример:

```groovy
conclude : error [
    id = "noOperandsFound";
    exception = true;
    exceptionName = "NoOperandsFound";
];
```

Что дает такая пометка:

- **вывод в CLI.** [Рассуждатель](../../4.%20Инструменты/CLI.md#its_reasoner-reasoner-cli) отдельно перечисляет все исключительные результаты, встреченные в трассе, в виде `id=...; result=...; exceptionName=...` (в JSONL - событием `branchResultExceptions`);
- **всплытие из субинтерпретаторов.** Если граф, вызванный через [[./Субинтерпретаторы.md|`subcall`/`subcall_mut`]], завершился таким узлом, вызывающий граф не получает обычный результат, а прерывается исключением `SubinterpreterException` с трассой вызванного графа. Это позволяет не "проглатывать" аварийные ситуации при вложенных вызовах;
- **отметку в трассе.** В человекочитаемой трассе рядом с узлом печатается `exceptionName=...`.

## Ключи наводящих вопросов

Данные ключи используются проектом [[../../3. Наводящие вопросы (its_QuestionGen)/Об its_QuestionGen.md|its_QuestionGen]] для порождения текста диалога с учащимся. Все они **локализованы** (т.е. записываются с префиксом кода локализации, например `RU.question`) и являются шаблонами: в их значениях допустима подстановка выражений - см. [[../../3. Наводящие вопросы (its_QuestionGen)/Шаблонизация текстов.md|«Шаблонизация текстов»]].

| Ключ                        | К каким элементам применяется | Назначение | Обязательность | Пример |
| --------------------------- | ----------------------------- | ---------- | -------------- | ------ |
| `question`                  | узлы вопроса, узлы, части кортежного вопроса | Формулировка вопроса, задаваемого учащемуся. | Нет: для `QuestionNode` и `WhileCycleNode` при отсутствии текст генерируется из выражения узла. | — |
| `asNextStep`                | любой узел | Шаблон формулировки данного узла как следующего шага. | Да | «Необходимо проверить, нужен ли ${X}[case('д')] левый операнд». |
| `endingCause`               | любой узел | Объясняет завершение рассуждения. | Да, если узел имеет выходы в красный или зелёный узел результата. | «Потому что ${X} не требует левого операнда». |
| `description`               | узлы агрегации, ветви мысли | Шаблон описания результата данного узла. Допускает уточнение для каждого результата: `description_correct`, `description_error`, `description_null`. | Да для агрегаций; нет для ветвей мысли. | «${X} ${$branchResult == BranchResult:CORRECT ? '' : 'не'} может выполниться следующим». |
| `text`                      | переходы, ожидаемые результаты частей кортежного вопроса | Шаблон текста данного варианта ответа. | Нет | «Приоритет ${X.class()}[case('р')] больше». |
| `explanation`               | переходы, ожидаемые результаты, категории ошибок поиска | Объяснение варианта ответа. | Да для [категорий ошибок поиска](./Способы%20описания/LOQI2.md#категории-ошибок-поиска); иначе нет. | — |
| `nextStepQuestion`          | переходы, ветви мысли | Для переходов — шаблон вопроса о том, что делать дальше при данном ответе; для ветвей мысли — о том, с чего начать в ветке. | Нет, но рекомендуется. | «Как определяется порядок выполнения операторов, имеющих разные приоритеты?» / «С чего надо начать при рассмотрении внутреннего операнда?» |
| `nextStepBranchResult`      | переходы, ветви мысли | Шаблон формулировок для красных и зелёных узлов при данном ответе. Допускает уточнение по результату (`..._correct` и т. д.). | Нет | «Оператор с ${$branchResult == BranchResult:CORRECT ? 'большим' : 'меньшим'} приоритетом всегда выполняется первым». |
| `nextStepExplanation`       | переходы, ветви мысли | Для переходов — шаблон объяснения того, что на самом деле делать дальше при данном ответе; для ветвей мысли — того, с чего на самом деле нужно начать в ветке. | Для переходов — нет, но рекомендуется; **для ветвей мысли — да** (при отсутствии вопрос о начале ветви не построится). | «Это неверно. Оператор с большим приоритетом всегда выполняется первым…» / «Это неверно. Прежде всего необходимо проверить, нужен ли оператору внутренний операнд». |
| `triviality`                | узлы вопроса | Текст, выдаваемый вместо вопроса, если узел оказался тривиальным по `trivialityExpr`. | Нет | — |
| `nullFormulation`           | узлы агрегации | Формулировка варианта «результат не влияет» в вопросе-сопоставлении о результатах веток. По умолчанию — системное «Не влияет». | Нет | — |
| `bodyNextStepQuestion`      | узлы последовательной агрегации (`WhileCycleNode`) | Шаблон вопроса о том, что делать дальше после проверки условия цикла. | Нет | — |
| `bodyNextStepExplanation`   | узлы последовательной агрегации (`WhileCycleNode`) | Задумывался как объяснение к предыдущему вопросу, но **в текущей версии `its_QuestionGen` не используется**. | Нет | — |

О том, в какой момент диалога каждый из этих ключей читается и во что превращается, см. [[../../3. Наводящие вопросы (its_QuestionGen)/Категории наводящих вопросов.md|«Категории наводящих вопросов»]].

Помимо элементов графа, `its_QuestionGen` использует метаданные и у определений [модели предметной области](../Модель%20предметной%20области/Модель%20предметной%20области.md): `localizedName` у классов, свойств, отношений и значений перечислений, а также `question` / `assertion` у свойств и отношений - для автоматического порождения формулировок.
