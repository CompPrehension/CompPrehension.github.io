Для описания дерева (наряду с разрабатываемым дополнением для draw.io) было решено создать расширение языка [LOQI](../../Модель%20предметной%20области/Представления%20данных/LOQI.md), которое доступно с альфа-версий 3.0.0 [its_DomainModel](https://github.com/CompPrehension/its_DomainModel/tree/loqi2). Данный язык имеет рабочее название `LOQI2` и предназначен для описания узлов графа мыслительного процесса (Thought Process Graph, TPG). 

> [!warning] Язык LOQI2 всё еще находится на этапе своего активного развития, поэтому разработчикам стоит следить за возможными изменениями в данном языке.

По умолчанию, файлы с описанием графа TPG по умолчанию располагаются в папке разрабатываемого домена и имеют расширение `*.tpg` (в случае `main.tpg` - у графа нет имени, он является основным), вместо сериализованного `tree.xml`
Также поддерживаются имена `tree_<имя>.loqi`, `tpg_<имя>.loqi`.
Полный перечень допустимых имён файлов и правила определения имени графа приведены в разделе [«Файлы графов» модели решения задач](../../Модель%20решения%20задач%20(DomainSolvingModel).md#файлы-графов).
В данной заметке содержится описание поддерживаемых на данных момент [узлов графа](../Узлы.md) на языке LOQI2 и может являться справочным руководством, применимого при разработке собственного TPG

## Аспекты совместимости и ограничения

*Главные проблемы при разработке LOQI2:* [GitHub](https://github.com/CompPrehension/its_DomainModel/blob/loqi2/FUTURE.md)

- Генерация `LOQI2` из сериализованного представления графа (`xml`) поддерживается **в экспериментальном режиме**. Полученный код предназначен в первую очередь для анализа, а не для дальнейшей разработки
- Ряд синтаксических конструкций языка (фрагменты, лямбда-выражения, `merge`, перенаправления `out`) существует только на уровне разбора текста и **не сохраняется** в модели графа. Соответственно, они не могут быть восстановлены обратной кодогенерацией

## Базовое описание дерева

Каждый файл в данном формате состоит из одной структуры, описывающей графа и любого количества вспомогательных блоков (метаданных, фрагментов и лямбда-выражений). Соответственно, каждый файл может описать только один такой граф.

Структура, описывающая граф, имеет следующий формат:

```groovy
tpg GraphName(inputVar1: T, inputVar2: T, defaultVar: T = defaultExpression) {
    // здесь описываются непосредственно узлы графа, начиная с корня
} [
    // блок метаданных, может быть опущен вместе с квадратными скобками
]
```

В данном фрагменте, переменные в скобках объявляют входные переменные графа, значения которых подаются вместе с самим графом в рассуждатель. У переменных также может быть значение, которое будет присвоено при объявлении в графе. Вместо `defaultExpression` прописывается стандартное [выражение для данной модели](../Выражения.md)

Блок метаданных имеет формат:

```groovy
meta for MetaAlias [
    attr=value;
]
```

Данный блок представляет собой отдельно стояющую (standalone) структуру, которая может подключаться в дальнейшем к каждому узлу или переходу в графе, добавляя свое содержимое как метаданные в выбранный элемент (в `xml` будет каждый элемент метаданных представляется как атрибут узла с `_` в начале со значением). Например, это может быть полезно для наводящих вопросов.
Один и тот же блок может быть подключен сразу к нескольким элементам графа - в этом случае его содержимое копируется в каждый из них. При этом блок, который не подключен ни к одному элементу, считается ошибкой (`Unused metadata with identifier ...`).

> [!note] Данный язык поддерживает однострочные комментарии `//` и многострочные `/* ... */`, как и оригинальный LOQI

## Концепция перенаправления потока описания графа

При разработке языка описания графа перед нами стояла задача обеспечить читаемость и удобство написания кода, попытаться сохранить привычные концепции императивных языков программирования. Граф мыслительных процессов и его реализация имеют главную проблему для реализации этой задачи - вложенность. Каждый дочерний узел вкладывается в родительский, многие узлы позволяют создавать произвольные разветвления. Поэтому, мы решили ввести в язык синтаксическую возможность "разворачивать" разветвления в графе, так, чтобы уменьшить вложенность, о котором будет рассказано в этом разделе

Представим некий абстрактный язык, описывающий граф, где каждый узел разветвлен и вкладывается в родительский (или неявный корень графа) выглядит в коде как:

```
node(...) {

} else {

}
```

или может иметь *n* веток:

```
branches {
    branch1 -> {

    }
    branch2 -> {

    }
    // и т.д. ... 
}
```

Кроме того, есть особый узел `finish;`, который сигнализирует о конце ветви графа

Обычный граф из таких узлов (без синтаксических "ухищрений") выглядит так:

```
node1(expr1) {
    branches1 {
        branch1 -> {
            node2(expr2) {
                // body 1-1-1-2
                finish;
            } else {
                // body 1-1-1-2-else
                finish;
            }
        }
        branch2 -> {
            // body 1-1-2
            finish;
        }
    }
} else {
    //body 1-else
    finish;
}
```

У этого кода графа есть одна ключевая особенность, которая кардинально отличает его от императивных языков программирования - отсутствие следования. Нет последовательного описания двух узлов. В применяемых на практике графах (где вложенности еще больше) это значительно снизит восприятие кода разработчиком
Чтобы обеспечить следование в таком графе мы можем ввести особую инструкцию (назовем ее `out`), который вынесет ветвь на уровень выше и продолжит описывать эту ветвь после узла, из которого мы вынесли ветвь:

```
node1(expr1) out else {
    //body 1-else
    finish;
}
branches1 {
    branch1 -> {
        node2(expr2) {
            // body 1-1-1-2
            finish;
        } else {
            // body 1-1-1-2-else
            finish;
        }
    };
    branch2 -> out;
}
// body 1-1-2
finish;
```

Подобный компромисс позволяет улучшить восприятие кода этого графа, и его можно применить в случае нашего графа мыслительных процессов. Конкретное применение в синтаксисе `loqi2` будет описано в следующих разделах

## Поддерживаемые узлы

### Ветвь мысли и узел результата ветви мысли

Каждая ветвь мысли в синтаксисе описывается в следующем формате:

```groovy
{
    // другой узел и его перенаправленные ветви
};
```

Если эта ветвь указана после `->` (или стрелочки с метаданными, о чем будет сказано [ниже](#метаданные)), вместо нее можно написать `out;` (обязательно с точкой с запятой), и она будет перенаправлена, как было описано в предыдущем разделе

При этом ветвь мысли обязательно должна завершаться результатом. Узел результата ветви мысли выглядит в следующем формате:

```groovy
conclude : correct;
```

Где `correct` - пример результата. **Подробнее про результаты:** [[../Узлы.md#результаты-ветвей-мысли|Результаты ветвей мысли]]
Верное заключение ("зеленый узел") ветви мысли может быть описано как `correct`, `true`, а ложное ("красный узел") - `error`, `false`, неопределенный результат как `null`.

Узел результата может выполнить произвольное [выражение](../Выражения.md) перед завершением ветви (`BranchResultNode.actionExpr`). Для этого после результата указывается блок `with (...)`:

```groovy
conclude : null with (X.state = State:evaluated);
```

Выражение может быть и блоком, если нужно выполнить сразу несколько действий:

```groovy
conclude : null with ({
    X.state = State:evaluated;
    X.value = 1;
});
```

### Узел вопроса

> **Основное описание узла:** [[../Узлы.md#обычный-вопрос-questionnode|QuestionNode]]

Вопрос представляется в языке:

```groovy
ask (expr) {
    expr1 -> {
        // ...
    };
    expr2 -> {
        // ...
    };
    // ...
};
```

> [!tip]
> Здесь и далее все выражения (описываемые как `expr`) имеют синтаксис, который был описан в [данной странице](../Выражения.md)

Перенаправление ветви в нем поддерживается (как было описано в разделе про ветвь мысли)

Однако, разработчикам не всегда требуется больше двух разветвлений в вопросе, зачастую достаточно вопроса формата "да/нет", и поэтому поддерживается сокращенное описание вопроса с применением перенаправления ветвей:

```groovy
ask (expr) out true else {
    // узлы ответа false...
};
// узлы ответа true...
```

В данной конструкции разработчик сам определяет, какую ветвь перенаправить на уровень выше. В примере - это `true` ответ вопроса. Стоит отметить, что данный синтаксис описания поддерживается только с ответами вопроса типа `bool` и не сработает с другими типами (приведет к ошибке разбора графа)

Если один и тот же код должен обрабатывать несколько ответов, их можно перечислить в одной ветви через запятую. Эта возможность описана в разделе [Многоключевые ветви](#многоключевые-ветви) - вместе с остальными средствами переиспользования кода.

#### Тривиальность вопроса

Узел вопроса может быть помечен как тривиальный - т.е. очевидный для учащегося, на котором не стоит заострять его внимание. Тривиальность напрямую не используется при прорешивании, а является вспомогательной информацией для сторонних проектов (в первую очередь для [наводящих вопросов](../../../3.%20Наводящие%20вопросы%20(its_QuestionGen)/Об%20its_QuestionGen.md)).

Есть два способа это сделать:

- Ключевое слово `switch` - узел безусловно считается тривиальной развилкой (`QuestionNode.isSwitch`):

  ```groovy
  ask switch (expr) {
      // ...
  };
  ```

- Блок `with trivial [...]` - предикат тривиальности (`QuestionNode.trivialityExpr`), т.е. булево выражение, вычисляемое при прорешивании:

  ```groovy
  ask (expr) with trivial [ X.state == State:evaluated ] out true else {
      // ...
  };
  ```

### Узел вопроса с кортежем

> **Основное описание узла:** [[../Узлы.md#вопрос-с-кортежем-с-несколькими-частями-tuplequestionnode|TupleQuestionNode]]

Вопросы с кортежем описываются c помощью ключевого слова `tuple`:
```groovy
ask tuple (expr1 ; expr2 ; expr3) {
    (expr1 ; expr2) -> {

    }
    (expr3 ; expr2) -> {

    }
};
```

В заголовке вопроса может быть произвольное число выражений (но не менее двух), представляющих `TupleQuestionNode.parts`. Части разделяются точкой с запятой, поскольку запятая уже используется внутри выражений.

Выражением каждой ветви является кортеж, представляющий набор выражений (произвольное количество)

#### Ожидаемые результаты частей вопроса

Каждая часть вопроса объявляет список ожидаемых результатов (`TupleQuestionPart.possibleOutcomes`). Они не используются при прорешивании и нужны сторонним проектам, чтобы знать полный набор возможных ответов на часть вопроса. Список указывается в блоке `with [...]` сразу после выражения части:

```groovy
ask tuple (
    X.state with [State:evaluated, State:unevaluated] ;
    X=>isOperandOf(Y) with [true, false]
) {
    (State:evaluated ; true) -> {
        // ...
    }
    // ...
};
```

В качестве значения результата допускаются литералы-значения (числа, строки, булевы значения, значения перечислений), ссылки `class:Name` и `obj:name`, а также результаты ветвей `correct`/`error`/`null`.

> [!warning]
> Синтаксически блок `with [...]` необязателен, но **валидация требует, чтобы у каждой части было не менее двух ожидаемых результатов**. Поэтому фактически его нужно указывать всегда - иначе валидация графа завершится ошибкой `... must contain at least two outcomes`.

Как сама часть вопроса, так и каждый её ожидаемый результат могут иметь метаданные - для этого используется уже знакомое ключевое слово `as` (подробнее в разделе [Метаданные](#метаданные)):

```groovy
ask tuple (
    X.state with [
        State:evaluated as evaluatedOutcome,
        State:unevaluated as unevaluatedOutcome
    ] as statePart ;
    X=>isOperandOf(Y) as operandPart
) {
    // ...
};
```

**Ограничения:** конструкция `ask tuple` не поддерживает `out` перенаправление потока описания графа

### Узел действия поиска

> **Основное описание узла:** [[../Узлы.md#действие-поиска-найти-объект-и-запомнить-findactionnode|FindActionNode]]

Действие поиска представлено в LOQI2, как уже известное нам объявление переменной в императивных языках программирования, которое особенно сильно его напоминает, если произвести перенаправление потока описания графа по результату `true`

Полная запись:

```groovy
var ID : T = expr {
    true -> {

    }
    false -> {

    }
};
```

> `ID` является произвольным именем переменной, а `T` - её объектным типом

Рекомендуемая запись с перенаправлением:

```groovy
var ID : TYPE = expr out true else {

};
```

В данном случае, если выражение не найдено для переменной, то присвоения не будет и граф перейдет в блок `false`, который обработает этот случай

Если ветви не указаны вообще, узел считается всегда успешным, и его единственный переход по `true` автоматически соединяется со следующей инструкцией:

```groovy
var X : Operator = find Operator x { $x=>isOperandOf(Y) };
// здесь описание продолжается так, как если бы был написан `out true`
```

В описании узла действия поиска также допускается производить дополнительные присваивания переменных дерева (произвольное количество) при условии, что результат поиска `true`. В синтаксисе конструкция изменяется:

```groovy
var ID : T with (ID1 : T = expr, ID2 : T = expr) = expr out true else {

};
```

Для полной записи аналогично добавляется в заголовок конструкция `with (declarations)`

#### Категории ошибок поиска

Узел поиска может объявить список категорий ошибок (`FindActionNode.errorCategories`) - вспомогательную информацию о том, почему найденный (или ошибочно выбранный учащимся) объект является ошибочным. При прорешивании категории не используются, но применяются сторонними проектами.

Категории описываются в блоке `error(...)` перед знаком `=`:

```groovy
var X : Operand error(
    1: Operand as wrongPlacement -> $checked=>isRightOf(Y),
    2: Operand -> $checked.state == State:unevaluated
) = expr out true else {
    // ...
};
```

Здесь:

- число перед `:` - приоритет категории (`FindErrorCategory.priority`), где 1 - наивысший;
- далее указывается тип проверяемого объекта;
- необязательное `as ID` задает псевдоним блока метаданных категории;
- после стрелки записывается предикат категории (`FindErrorCategory.selectorExpr`). Проверяемый объект доступен в нем как контекстная переменная `$checked`.

### Агрегации

Прежде всего, стоит отметить, как обозначаются методы агрегации в коде `LOQI2`:

- `SIM:AND` в данном языке обозначается ключевым словом `and`
- `SIM:OR` в данном языке обозначается ключевым словом `or`
- `HYP` в данном языке обозначается ключевым словом `hyp`
- `MUTEX` в данном языке обозначается ключевым словом `mutex`

В разделах ниже метод агрегации будет обозначен просто как `AGG`

#### Узел агрегации по ветвям

> **Основное описание узла:** [[../Узлы.md#узел-агрегации-по-ветвям-branchaggregationnode|BranchAggregationNode]]

Узел агрегации по ветвям описываются в языке следующим образом:

```groovy
agg AGG {
    correct -> {

    }
    error -> {

    }
    body1 -> {

    }
    body2 -> {

    }
};
```

Данная запись совмещает в фигурных скобках сразу два типа ветвей - ветви агрегации и ветви результата
Ветви результата могут иметь значения: `true`/`correct`, `false`/`error`, `null` (аналогично [узлам результата](#Ветвь-мысли-и-узел-результата-ветви-мысли)). Одна из этих ветвей может быть перенаправлена в отличие от ветвей агрегации
Ветвей агрегации может быть произвольно много, каждая из ветвей имеет свой идентификатор, который не сохраняется в итоговой модели (существует только в синтаксисе языка), а предназначен только для различения ветвей разработчиком графа. Идентификатор задается разработчиком произвольно, и может быть назван как `_`.

Для данного узла также допускается сокращенная запись с перенаправлением

```groovy
agg AGG {

} out true;
```

Здесь только одна ветвь агрегации (без идентификатора), и только один перенаправленный результат (в данном случае `true`)

#### Циклы агрегации

> **Основное описание узла:** [[../Узлы.md#узел-агрегации-в-цикле-по-объектам-cycleaggregationnode|CycleAggregationNode]]

Цикл агрегации синтаксически схожи с [узлами агрегации по ветвям](#узел-агрегации-по-ветвям) отличается тем, что в нем описывается только одна ветвь агрегации, копии которой порождаются на этапе выполнения в зависимости от выражения, и затем агрегируются по указанному методу

```groovy
cycle AGG (expr) with T ID {
    true -> {

    }
    false -> {

    }
    body -> {

    }
};
```

или сокращенная запись

```groovy
cycle AGG (expr) with T ID {

} out true;
```

Стоит еще раз отметить, что у цикла только одна ветвь агрегации, и описание нескольких ветвей агрегации приведет к ошибке семантического анализатора

Также, описание переменной цикла несколько отличается от предыдущих объявлений переменной, в отличие от стиля `ID : T`, здесь используется стиль `T ID`, где тип указывается до идентификатора переменной и не разделяется другим токеном.

Цикл агрегации, как и [узел действия поиска](#узел-действия-поиска), поддерживает [категории ошибок](#категории-ошибок-поиска) - блок `error(...)` записывается сразу после выражения предиката поиска:

```groovy
cycle and (expr) error(
    1: Operand -> $checked.state == State:unevaluated
) with Operand Op {

} out true;
```

### Цикл while

> **Основное описание узла:** [[../Узлы.md#узел-последовательной-агрегации-whilecyclenode|WhileCycleNode]]

Цикл while описывается аналогично циклу агрегации, так же имеет только одну ветвь тела, но не имеет метода агрегации и переменной цикла. По синтаксису он наиболее приближен к своему аналогу в императивных языках (вроде Си)

Полная запись:

```groovy
while (expr) {
    true -> {

    }
    body -> {

    }
};
```

Сокращенная запись:

```groovy
while (expr) {

} out true;
```

Здесь, как и ранее в сокращенных записях: в фигурных скобках - тело цикла, а в перенаправлении - только одна ветвь результата

## Вызовы процедур

Помимо основных узлов графа, в языке существуют **вызовы** - обращения к процедурам, зарегистрированным в `its_DomainModel` и реализованным в `its_Reasoner`.

Вызов в `LOQI2` представляет собой следующий синтаксис:
`ID(expr1, expr2, expr3)` или `ID()`, кроме того `ID` может быть как просто идентификатором, так и цепочкой разрешения пространства имен, например: `ID:ID`

Вызовы могут употребляться в двух позициях:

- **как инструкция графа** - тогда вызов становится отдельным узлом графа (`ProcedureCallNode`), у которого ровно один переход - к следующей инструкции;
- **как выражение** - тогда вызов является частью [выражения](../Выражения.md) (`CallProcedure`) и должен иметь возвращаемый тип.

Пространства имен процедур на данный момент следующие:

| Пространство | Назначение                                                                          |
| ------------ | ----------------------------------------------------------------------------------- |
| *(без имени)* | Процедуры общего назначения (`eval`, `subcall`, `subcall_mut`, `assert`)             |
| `debug`      | [Отладочные вызовы](#отладочные-вызовы), недопустимые в production-графах            |
| `fragment`   | [Фрагменты](#фрагменты) - макросы уровня разбора текста                              |
| `lambda`     | [Лямбда-выражения](#лямбда-выражения) - макросы уровня разбора выражений             |

### Отладочные вызовы

Разработчику зачастую требуется проверять граф на рассуждателе `its_Reasoner`, однако отладка ограничивается только анализом трассы рассуждателя. Для удобства разработки с применением `LOQI2` были внедрены отладочные процедуры пространства имен `debug`:

- `debug:print(obj)` - принимает один аргумент любого типа и печатает его строковое представление, когда рассуждатель достигает узел этого вызова, а затем переходит к следующему узлу графа. Данная процедура заменила ранее существовавшие `debug:point` (из alpha-версий 3.0.0)
- `debug:dump(comment)` - принимает строковый комментарий; выводит его, а следом дамп всех переменных дерева, доступных рассуждателю в момент достижения узла вызова (а при вызове внутри выражения - также и переменных текущей области видимости)
- `debug:trace(expr)` - принимает **выражение** (а не его значение), вычисляет его и печатает подробную трассу вычисления, после чего возвращает полученное значение. Может использоваться как выражение внутри других выражений
- `debug:breakpoint(comment)` - точка останова: рассуждатель прерывает свою работу, выбрасывая `ReasonerBreakpointException` с указанным комментарием
- `assert(condition, message)` - проверка условия (процедура общего назначения, не из `debug`). Рассуждатель выполняет проверку условия и в случае `false` прерывает рассуждение с сообщением `message`

Пример:

```groovy
debug:print("Начинаем проверку операнда");
var X : Operand = find Operand x { $x=>isOperandOf(Y) } out true else {
    debug:dump("Операнд не найден");
    conclude : error;
};
ask (debug:trace(X.state == State:evaluated)) out true else {
    conclude : error;
};
```

> [!warning] Отладочные вызовы и production-графы
> Данные вызовы крайне рекомендуется использовать только в окружениях разработки и не оставлять в итоговом варианте графа.
> Это требование проверяется автоматически: `DomainSolvingModel.validate(debug)` при `debug = false` (значение по умолчанию) выбрасывает ошибку, если в дереве найдены вызовы процедур из пространства имен `debug`. Соответственно, [CLI-команды](../../../4.%20Инструменты/CLI.md) имеют флаг `--debug`, который отключает эту проверку.

Также, стоит отметить, что сообщения передаваемые как аргументы НЕ поддерживают на данный момент какую-либо интерполяцию выражений/переменных

### Выполнение произвольного выражения

Процедура `eval(expr)` выполняет переданное выражение и ничего не возвращает. Она нужна там, где по смыслу требуется "узел действия", которого в модели графа нет:

```groovy
eval(X.state = State:evaluated);
```

> [!danger] Использование eval без крайней необходимости нежелательно (только, если без нее никак не реализовать), поскольку вычисление отдельного выражения в ветви мысли плохо вписывается в модель мыслительного процесса. Предпочтительнее использовать узел результата с передаваемым через него выражением в `with(...)`

Также `eval` используется построителем неявно: если [фрагмент](#фрагменты) перенаправляется через `out`, а его узел результата содержал `with (...)`, то это действие сохраняется в виде узла `eval` перед точкой соединения.

### Субинтерпретаторы

Процедуры `subcall` и `subcall_mut` запускают **другой граф** из этого же `DomainSolvingModel` как подпрограмму:

```groovy
subcall("check_operands", X, Y)
subcall_mut("apply_evaluation", true, X, Y)
```

- Первым аргументом идет имя вызываемого графа, далее - объекты, подставляемые в его входные переменные (аргументов может быть произвольное количество - по числу переменных вызываемого графа)
- У `subcall_mut` вторым аргументом идет булев флаг `restore_variables`: если он `true`, то переменные дерева, полученные в вызванном графе, переносятся в вызывающий граф
- Обе процедуры возвращают значение [встроенного перечисления](../../Модель%20предметной%20области/Перечисления%20(Enum).md) `OptionalBool` (`OptionalBool:true` / `OptionalBool:false` / `OptionalBool:null`), соответствующее результату вызванного графа. При необходимости оно приводится к `bool` (где `OptionalBool:null` считается `false`)

Как и любой [вызов процедуры](#вызовы-процедур), субинтерпретатор может употребляться и как инструкция графа, и как часть выражения. Кроме того, его результат можно сделать результатом текущей ветви мысли напрямую - для этого он указывается прямо в `conclude` (в модели это узел `BranchResultRedirectingNode`):

```groovy
conclude : subcall("check_operands", X, Y);
```

> [!tip]
> Здесь описан только синтаксис вызова. О том, что такое субинтерпретаторы, чем `subcall` отличается от `subcall_mut` по смыслу, как ведет себя состояние модели при вызове и в каких случаях выносить рассуждение в отдельный граф вообще стоит, читайте в отдельной статье: [[../Субинтерпретаторы.md|Субинтерпретаторы]]

## Шаблонизация и переиспользуемость кода

По мере роста графов в них появляются повторяющиеся куски: одинаковые последовательности проверок, одинаковые условия в разных узлах, одинаковые "хвосты" ветвей, несколько ответов, обрабатываемых совершенно одинаково. Чтобы не дублировать такой код **в исходном тексте**, в `LOQI2` введены четыре механизма: **многоключевые ветви**, **фрагменты**, **лямбда-выражения** и оператор **merge**.

> [!important]
> Все они работают **только на этапе разбора текста** и являются макросами: они разворачиваются (встраиваются) в месте использования, и в итоговой модели графа от них не остается никаких следов. Соответственно:
> - обратная [кодогенерация](#экспериментальная-кодогенерация-loqi2) их не восстанавливает;
> - рекурсивные вызовы фрагментов и лямбда-выражений запрещены и приводят к ошибке сборки (`Recursive fragment expansion detected` / `Recursive lambda expansion detected`);
> - **и, самое главное, все они дублируют узлы в итоговой модели.** Об этом в разделе [Цена дублирования узлов](#цена-дублирования-узлов).

### Многоключевые ветви

Если несколько ответов узла должны обрабатываться одним и тем же кодом, их можно перечислить в одной ветви через запятую - вместо того, чтобы писать этот код несколько раз:

```groovy
ask (X.state.compare(Y.state)) {
    Comparison:less, Comparison:equal -> {
        conclude : error [ skill = "operand_order" ];
    };
    Comparison:greater -> out;
};
```

Такая запись поддерживается везде, где ветви задаются явно: в узлах вопроса, в узлах поиска, в узлах агрегации и в циклах. Ключи могут быть как выражениями (ответами узла), так и результатами ветвей (`correct`, `error`, `null`) - в зависимости от вида узла.

> [!warning]
> Многоключевая ветвь **не создает один общий узел для нескольких ответов**. Тело ветви строится заново для каждого перечисленного ключа, поэтому запись `a, b, c -> { ... }` даст в модели **три независимые копии** описанного поддерева.

Перенаправление в `out` тоже перечисляется через запятую:

```groovy
ask (expr) {
    Comparison:less, Comparison:equal -> out;
    Comparison:greater -> {
        conclude : error;
    };
};
// продолжение, общее для less и equal
```

Такая запись строит продолжение один раз, и в модели, собранной из текста, все перечисленные ключи получают переходы в **один и тот же** объект узла. Однако разделяемый узел не переживает сериализацию: `xml` - дерево, и продолжение выписывается в нем отдельным поддеревом для каждого ключа, а после обратной загрузки из `xml` это уже независимые копии. Поэтому на итоговый размер графа многоключевой `out` влияет так же, как и многоключевая ветвь с телом - дублирование присутствует и здесь.

### Фрагменты и лямбда-выражения

#### Фрагменты

**Фрагмент** - это именованный кусок графа (ветвь мысли), который можно встроить в произвольное место. Объявляется он рядом с описанием графа (до или после него) ключевым словом `fragment`:

```groovy
fragment checkEvaluated(Op: Operand) {
    ask (Op.state == State:evaluated) out true else {
        conclude : error [
            skill = "unevaluated_operand";
        ];
    };
    conclude : correct;
}
```

Аргументы фрагмента - это **ссылки на переменные графа**, а не произвольные выражения. Поэтому:

- при вызове в качестве аргументов можно передавать только имена переменных графа;
- аргументы не могут иметь значения по умолчанию;
- внутри тела фрагмента имя формального аргумента подставляется на имя переменной из места вызова.

Вызов фрагмента синтаксически идентичен обычному [вызову процедуры](#вызовы-процедур), но с двумя обязательными условиями:

- **пространство имен `fragment` указывать обязательно.** Без него имя не разрешается как фрагмент, и построитель ищет процедуру с таким именем - сборка падает с `Procedure ... not found` (а при наличии перенаправления результатов - с `Call result redirection is supported only for fragments`);
- **`fragment` - ключевое слово языка**, поэтому в позиции имени его нужно экранировать обратными кавычками, как любой другой экранированный идентификатор в LOQI. Без экранирования лексер выдаст токен ключевого слова, и разбор завершится синтаксической ошибкой.

Таким образом, единственная рабочая форма вызова:

```groovy
tpg MyGraph(X: Operand, Y: Operand) {
    `fragment`:checkEvaluated(X);
    // ...
}
```

> [!warning]
> Записи `checkEvaluated(X)` и `fragment:checkEvaluated(X)` **не работают** - первая не находит фрагмент, вторая не проходит синтаксический разбор из-за ключевого слова fragment. Это отличает фрагменты от [лямбда-выражений](#лямбда-выражения), у которых пространство имен необязательно.

**Перенаправление результатов фрагмента.** Тело фрагмента обязано завершаться узлами результата, но в месте вызова зачастую нужно продолжить рассуждение, а не завершить ветвь. Для этого вызов фрагмента поддерживает такие же перенаправления, как и узлы графа: подходящие `conclude` в теле фрагмента заменяются на указанные разработчиком продолжения. Если же тип узла завершения не указан в `out`, то фрагмент вставит его в итоговое дерево "как есть", и он будет считаться завершающим узлов ветви, где встроен фрагмент, а не завершающим узлом фрагмента. Данный нюанс стоит учитывать при разработке собственных фрагментов и заранее проектировать, какие выходы завершат сам фрагмент, а какие нужно встроить внутрь ветви

Сокращенная запись выносит один или несколько результатов "наружу", к следующей инструкции:

```groovy
`fragment`:checkEvaluated(X) out correct;
// сюда попадет исполнение, если фрагмент завершился с `conclude : correct`
ask (X=>isOperandOf(Y)) out true else {
    conclude : error;
};
conclude : correct;
```

Полная запись позволяет для каждого результата задать свою ветвь (или тоже отправить его в `out`):

```groovy
`fragment`:checkEvaluated(X) {
    correct -> {
        conclude : null with (X.state = State:evaluated);
    };
    error -> out;
};
// сюда попадет исполнение, если фрагмент завершился с `conclude : error`
conclude : error;
```

Ограничения перенаправления:

- один и тот же результат нельзя перенаправить дважды (`Duplicate fragment result redirection`);
- перенаправлять можно только результаты ветвей (`correct`/`error`/`null`), но не произвольные выражения;
- нельзя перенаправить `conclude`, который является **началом вложенной ветви мысли** (например, единственной инструкцией тела цикла или ветви агрегации) - такой `conclude` принадлежит логике самого узла, а не является выходом фрагмента;
- если перенаправление указано, но продолжения после вызова нет, это ошибка сборки (`Fragment call redirects ... to out, but there is no following statement`).

> [!warning]
> Встраивание фрагмента означает "построить его тело здесь заново", а не "переиспользовать готовое поддерево". Так сделано намеренно - чтобы метаданные, псевдонимы и перенаправления оставались локальными для места вызова, - но это значит, что в модели окажется **столько копий тела фрагмента, сколько раз он был вызван**. См. [Цена дублирования узлов](#цена-дублирования-узлов).

#### Лямбда-выражения

**Лямбда-выражение** - это то же самое, что и фрагмент, но на уровне [выражений](../Выражения.md): именованное выражение с параметрами, которое подставляется в месте вызова. Объявляется ключевым словом `lambda`:

```groovy
lambda isUnevaluatedOperandOf(Op: Operand, Expr: Operator) =
    $Op.state == State:unevaluated and $Op=>isOperandOf($Expr);
```

> [!note]
> Объявление лямбда-выражения обязательно завершается точкой с запятой.

В отличие от фрагментов, аргументами лямбда-выражения могут быть **произвольные выражения**, а не только переменные дерева - они подставляются в тело "как есть":

```groovy
ask (isUnevaluatedOperandOf(X, Y)) out true else {
    conclude : error;
};
```

В отличие от фрагментов, пространство имен у лямбда-выражения **необязательно**: разрешение имени происходит по имени и по количеству аргументов, поэтому лямбда-выражение не будет спутано с процедурой другой арности. Полная запись с пространством имен также допускается, но `lambda` - тоже ключевое слово языка, поэтому его требуется экранировать обратными кавычками: `` `lambda`:isUnevaluatedOperandOf(X, Y) ``. Запись `lambda:isUnevaluatedOperandOf(X, Y)` без экранирования не проходит разбор.

Лямбда-выражения дублируют не узлы, а сами выражения: каждое использование добавляет в модель полную копию тела. Узлов от этого не прибавляется, но выражения в них растут - что тоже стоит учитывать, особенно если лямбда-выражение объемное и используется внутри цикла.

### Оператор merge

> [!danger] Применять только в ограниченных сценариях использования. Оператор может сломать поведение графа, что усложнит его отладку

Ветви графа в `LOQI2` описываются как вложенные блоки, поэтому "склеить" две ветви обратно в один узел синтаксически невозможно. `merge` **не решает** эту задачу и разделяемых узлов не создает - он решает более узкую: дотянуть до общего продолжения те ветви, которые не были перенаправлены через `out`.

`merge` означает: *"подставить сюда весь остаток описания"*. Построитель берет продолжение - все инструкции, оставшиеся после `merge` в текущем блоке, а затем все инструкции, оставшиеся после текущего блока в объемлющих блоках, - и **строит его в этом месте заново**.

> [!important] Узел с `merge` в ветвях обязан сохранять перенаправление `out`
> Продолжение после ветвящегося узла достижимо только через `out`: построитель умеет присоединить следующую инструкцию либо к узлу вызова процедуры, либо к узлу, у которого есть `out`-переход. Если ни одна ветвь узла не ушла в `out`, то продолжения у него просто нет - ни для самого узла, ни для `merge` внутри его ветвей, - и сборка завершается ошибкой `Statement can't be reached`.

Поэтому правильная схема применения такова: одна ветвь узла уходит в `out` и получает продолжение обычным путем, а остальные ветви дотягиваются до того же продолжения через `merge`.

Сокращенная запись:

```groovy
ask (X.state == State:evaluated) out true else {
    eval(X.value = 0);
    merge;
};
// общее продолжение обеих ветвей:
// ветвь `true` приходит сюда через `out`, ветвь `false` - через `merge`
ask (X=>isOperandOf(Y)) out true else {
    conclude : error;
};
conclude : correct;
```

Полная запись ветвей - при том же условии, что одна из ветвей перенаправлена в `out`:

```groovy
ask (X.state.compare(Y.state)) {
    Comparison:greater -> out;
    Comparison:equal -> {
        eval(X.value = 0);
        merge;
    };
    Comparison:less -> {
        conclude : error;
    };
};
// общее продолжение для `greater` и `equal`
conclude : correct;
```

А вот так граф **не соберется**:

```groovy
ask (X.state == State:evaluated) {
    true -> {
        eval(X.value = 1);
        merge;
    };
    false -> {
        eval(X.value = 0);
        merge;
    };
};
// Statement can't be reached
conclude : correct;
```

Здесь ни одна ветвь вопроса не перенаправлена в `out`, поэтому у вопроса нет перехода, к которому можно присоединить следующую инструкцию - и продолжения, которое `merge` мог бы скопировать, тоже не существует. Чтобы это исправить, достаточно отправить в `out` любую одну из ветвей, оставив `merge` в остальных.

> [!note]
> Диагностика этой ошибки зависит от того, чем именно начинается недостижимое продолжение: в части случаев построитель вместо `Statement can't be reached` падает с внутренней ошибкой `ThisShouldNotHappen` из `closeOutRedirect`. Причина при этом та же самая - у узла нет `out`-перехода.

Предостережения:

- `merge` **дублирует** узлы продолжения: в модели графа продолжение будет представлено отдельным поддеревом для каждого `merge`, плюс еще одним - для ветви, ушедшей в `out`. Это синтаксическое удобство, а не разделяемый узел, и здесь цена дублирования наиболее велика, поскольку дублируется не короткий фрагмент, а весь оставшийся "хвост" описания;
- `merge` должен быть **последней инструкцией в своем блоке**. Инструкции, записанные после него, не отбрасываются: они попадают внутрь встраиваемого продолжения, причем **перед** внешним хвостом. То есть `merge; foo;` фактически означает "выполнить `foo`, а затем внешнее продолжение" - порядок, обратный тому, как это читается. Писать так не стоит;
- если продолжения нет вообще (например, `merge` записан в самой последней инструкции графа), это ошибка сборки: `Merge statement has no continuation to merge`;
- `merge` внутри **ветви агрегации или тела цикла** синтаксически допустим, но почти наверняка означает не то, что задумано: продолжение встраивается *внутрь* этой ветви, и его узел результата становится результатом ветви агрегации, а не результатом графа. При этом то же самое продолжение будет построено еще раз после самого узла - по пути `out`.

### Цена дублирования узлов

Все описанные в этом разделе механизмы существуют **только в тексте на LOQI2**. Модель графа о них не знает: там, где разработчик написал одно, в модели окажется несколько.

| Механизм                             | Что дублируется                                        |
| ------------------------------------- | -------------------------------------------------------- |
| Многоключевая ветвь `a, b -> { ... }` | Тело ветви - по копии на каждый перечисленный ключ       |
| Многоключевой `a, b -> out`           | Продолжение - в модели один общий узел, но в `xml` (и после загрузки из него) по копии на каждый ключ |
| Вызов фрагмента                       | Все тело фрагмента - по копии на каждый вызов            |
| Лямбда-выражение                      | Все выражение - по копии на каждое использование         |
| `merge`                               | Все продолжение описания - по копии на каждый `merge`, плюс еще одна по пути `out` |

Дублирование при этом **перемножается**: фрагмент, вызванный из многоключевой ветви, будет встроен столько раз, сколько там ключей; `merge` внутри фрагмента размножит продолжение на каждый вызов фрагмента. Небольшой и аккуратно выглядящий исходник таким образом легко превращается в граф на многие сотни узлов.

Из этого следуют два практических последствия:

- **рассуждатель работает медленнее.** Он выполняет узлы модели, а не строки исходника: каждая копия узла - это отдельное вычисление выражения, отдельный шаг в трассе и отдельная запись состояния переменных. Особенно заметно это внутри циклов и агрегаций, где размноженное поддерево выполняется на каждой итерации;
- **читаемость сериализованного XML резко падает.** Один и тот же кусок логики встречается в `xml` многократно, но уже без каких-либо признаков того, что это копии одного и того же кода. Это осложняет и ручной разбор XML, и сопоставление трассы с исходником, и [обратную кодогенерацию](#экспериментальная-кодогенерация-loqi2) - она выведет все копии как независимые поддеревья.

> [!warning]
> Средства переиспользования кода нужно применять **осознанно и с осторожностью**. Они улучшают читаемость исходного текста ценой роста итоговой модели, и это не всегда выгодно.
>
> Практические ориентиры:
> - **предпочитайте `out` там, где он применим.** Обычное перенаправление одной ветви в продолжение не создает копий вообще - в отличие от `merge`, который весь оставшийся "хвост" описания дублирует. При этом многоключевой `a, b -> out` от дублирования не спасает: по копии продолжения на каждый ключ там все равно появится (в `xml` - сразу, в модели - после обратной загрузки из него);
> - **если выносимое рассуждение является самостоятельным графом** - с собственной целью, входными переменными и осмысленным результатом, - то его место не во фрагменте, а в отдельном графе, подключаемом через [[../Субинтерпретаторы.md|субинтерпретатор]]: такой граф существует в модели в единственном экземпляре и не дублируется при каждом вызове;
> - **не выносите во фрагмент то, что вызывается один раз** - это не дает выигрыша, но добавляет уровень косвенности;
> - **опасайтесь `merge` в начале длинного описания** - чем раньше по тексту стоит `merge`, тем больший "хвост" он размножит;
> - **следите за размером получившейся модели.** Если не уверены в цене конкретной конструкции, преобразуйте граф в XML (`domain-cli tree-loqi-to-xml`) и посмотрите на результат - это самый прямой способ увидеть реальное число узлов.

## Метаданные

Метаданные для графа мыслительных процессов также важны, поскольку сторонние проекты (такие как, [наводящие вопросы](../../../3.%20Наводящие%20вопросы%20(its_QuestionGen)/Об%20its_QuestionGen.md)) могут их использовать. Более того, эти метаданные могут быть присвоены абсолютно сущностям графа:

- графу
- узлам
- переходам между узлами
- вспомогательным сущностям: частям кортежного вопроса, их ожидаемым результатам, категориям ошибок поиска

При разработке `LOQI2` мы старались обеспечить максимальную поддержку описания метаданных, с сохранением удобства чтения графа. Метаданные в языке описываются так же, как и в [языке описания данных](../../Модель%20предметной%20области/Представления%20данных/LOQI.md)

```groovy
[
    meta1 = value1;
    meta2 = value2;
    // и т.д.
]
```

> [!note]
> В сериализованном XML формате графа все метаданные описываются как атрибуты узла с префиксом `_`

> [!tip]
> О том, какие ключи метаданных используются системой и что они означают, читайте в отдельной статье: [[../Соглашения о метаданных.md|Соглашения о метаданных узлов]]

### Узлы результата

Прежде всего, узлы результаты поддерживают описание метаданных прямо перед `;` как блок `[]`:

```groovy
conclude : error [
    skill="unevaluated_operator"
];
```

### Ссылки на блоки метаданных у узлов

Другие узлы также поддерживают метаданные, но в отличие от узла результата, было решено отказаться от прямого описания метаданных прямо рядом с описанием узла.
Вместо этого мы ввели ключевое слово `as` и в конце каждого описания узла, прямо перед `;` можно указать `as ID`, где `ID` - это псевдоним для блока метаданных, который можно описать уже вне графа. Пример:

```groovy
tpg MyTree(A: Answer) {
    // ...

    ask (isEvaluated) out true else {
        // ...
    } as evaluationAsk;

    // ...
}

// ... 

meta for evaluationAsk [
    skill="unevaluated_operator"
]
```

> Стоит отметить, что блоки метаданных не обязательно должны быть написаны после описания графа, они могут быть и перед ним

> [!tip]
> Узлы результатов поддерживают оба стиля: и прямое описание блока `[...]`, и ссылку `as ID`. Первый обычно удобнее, поскольку метаданные результата хочется видеть сразу рядом с описанием узла, но одновременно указать оба способа нельзя.

Так же, через `as ID`, описываются метаданные [частей кортежного вопроса и их ожидаемых результатов](#ожидаемые-результаты-частей-вопроса), а также [категорий ошибок поиска](#категории-ошибок-поиска).

### Метаданные у графа

Граф, так же как и узел результата, поддерживает описание метаданных сразу после описания дерева в блоке `[]` и не может быть перенаправлен через `as`

### Переходы и их метаданные

Переходы - узел в языке `LOQI2`, который не имеет своего явного синтаксического представления. Более того, переходы могут быть перенаправлены в данном языке (чего нет в самой модели). И для других проектов, таких как наводящие вопросы, переходы должны быть аннотированы метаданными

Чтобы поддерживать данную возможность, мы расширили два ключевых токена, связанных с переходами - `out` и `->`

В случае `->` все просто: она указывает на переход в определенную ветвь, например в ветвь агрегации. Поэтому, логично разрешить указывать псевдоним блока метаданных прямо в ней: `-[ID]->`. Таким образом:

```groovy
meta for myMeta [
    branch=1
]

// ...
agg AGG {
    true -[myMeta]-> {
        // ...
    }
    body -> {

    }
}
// ...
```

Но, в некоторых ситуациях, мы можем не описывать этот переход явно. Например, при использовании `out`:

```groovy
agg AGG {

} out true;
```

В этом случае, мы можем написать псевдоним метаданных прямо рядом с перенаправлением:

```groovy
agg AGG {

} out[myMeta] true;
```

В данной сокращенной записи у тела невозможно описать псевдоним метаданных, поэтому в таких случаях стоит использовать полную запись ветвей агрегации со стрелочками.

Также, немаловажным нюансом является невозможность задания одновременно `out()` и `-[]->`. Например:
```
agg AGG {
    // ...
    true -[myMeta]-> out[myMeta2];
    // ...
}
```
Это приведет к синтаксической ошибке.

> [!note]
> Метки ветвей агрегации (`body1`, `_` и т.п.) **не** являются псевдонимами метаданных - это чисто синтаксические идентификаторы, и попытка описать `meta for body1` приведет к ошибке.
