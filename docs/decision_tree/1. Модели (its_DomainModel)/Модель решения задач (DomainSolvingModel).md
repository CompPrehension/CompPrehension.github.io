**Модель решения задач** (или модель предметной области, в коде - `DomainSolvingModel`) - это формальное описание некоторой предметной области (домена) для построения и прорешивания различных учебных ситуаций в ней. Она состоит из нескольких компонентов:

- **общая [модель предметной области](Модель%20предметной%20области/Модель%20предметной%20области.md)** (`DomainSolvingModel.domainModel`) - описание классов, свойств, отношений и перечислений, общее для всех ситуаций применения;
- **теги** (`DomainSolvingModel.tagsData`) - части модели предметной области, специфичные для отдельных ситуаций применения. В конкретной учебной ситуации зачастую тег объединяется с общей моделью для получения нужной специфики;
- **[графы мыслительных процессов](Дерево%20решений/Дерево%20(граф)%20решений.md)** (`DomainSolvingModel.decisionTrees`) - графовые описания того, как должны решаться задачи в учебных ситуациях этой предметной области.

## Модель конкретной ситуации в предметной области

`DomainSolvingModel` описывает предметную область и способ решения задач в ней в целом, но не саму задачу. **Конкретная учебная ситуация в предметной области** (представляется объектом класса `DomainModel`) содержит в себе заполненные сущности предметной области конкретными данными (например, созданные объекты [классов](Модель%20предметной%20области/Классы.md), соединенные с помощью [отношений](Модель%20предметной%20области/Отношения.md)), которые уже отражают определенную учебную задачу в этой предметной области.

Пример создания модели конкретной ситуации:

```java
// общая модель + специфическая добавка к общей модели (из тега)
DomainModel subDomainModel = model.getMergedTagDomain(tagName);

// модель конкретной ситуации (содержит в себе общую модель с тегами и добавленные данные задачи)
DomainModel situationDomain = DomainLoqiBuilder.buildDomain(new FileReader(situationFileName));
situationDomain.addMerge(subDomainModel);
situationDomain.validateAndThrow();
```

Модели конкретной ситуации **не являются частью предметной области**, они лишь ссылаются на нее и дополняют, чаще всего они собираются динамически в коде, как правило, не экспортируются в файл, но в CLI инструменте, данная опция имеется.

Для решения учебной задачи в модели решения задач имеются графы мыслительных процессов. Граф мыслительных процессов использует созданную **модель конкретной ситуацию в предметной области** (как мы видим из примера, в нее уже вложена общая модель) как хранилище объектов, из которых будет происходить рассуждение над задачей, а также **переменные графа** -  объекты, взятые из конкретной ситуации, выступающие в роли входных переменных для графа. Модель конкретной ситуации в предметной области и переменные графа объединяются в библиотечном коде в структуру, именуемую как `LearningSituation`, которая относится уже к интерпретатору, а не к описанию и сущностям предметной области (т.е. находится в проекте `its_Reasoner`)

## Директория домена

На практике `DomainSolvingModel` почти всегда строится **из директории** - разработчик домена раскладывает файлы по определенным правилам, а модель собирает их сама. Эта страница описывает, из чего состоит такая директория, какие файлы в ней допустимы и как они идентифицируются.

Самый частый способ создать модель решения задач - указать путь к директории:

```java
DomainSolvingModel model = new DomainSolvingModel(
    directoryPath,
    DomainSolvingModel.BuildMethod.LOQI
);
model.validate();
```

Типичная директория выглядит так:

```
domain/
├── domain.loqi              # общая модель предметной области
├── tag_python.loqi          # тег поддержки языка Python в предметной области (пример тега)
├── tag_cpp.loqi             # тег поддержки языка C++ в предметной области (пример тега)
├── main.tpg                 # граф по умолчанию (без имени)
├── tpg_checkOperands.tpg    # граф с именем "checkOperands"
└── tree_legacy.xml          # граф с именем "legacy", в сериализованном виде
```

Общие правила сборки модели решения задач:

- **сканирование не рекурсивно.** Учитываются только файлы, лежащие непосредственно в указанной директории; вложенные папки не просматриваются;
- **файлы опознаются по имени.** Файл, имя которого не подходит ни под один известный шаблон, просто игнорируется;
- **директория может находиться в ресурсах приложения JVM.** При использовании библиотечного интерфейса моделью может быть и папка внутри jar файла

## Способы сборки (`BuildMethod`)

Модель предметной области может быть собрана двумя способами; выбор задается параметром `BuildMethod`.

### `LOQI` (основной)

Модель читается из файлов на языке [LOQI](Модель%20предметной%20области/Представления%20данных/LOQI.md):

| Файл                  | Что это                                                            |
| --------------------- | -------------------------------------------------------------------- |
| `domain.loqi`         | Общая модель предметной области. **Обязателен**                      |
| `tag_<имя тега>.loqi` | Модель тега с именем `<имя тега>`. Таких файлов может быть сколько угодно |

Это рекомендуемый способ: он же используется при записи модели обратно в директорию (`DomainSolvingModel.writeModelToDirectory`).

### `DICT_RDF` (устаревший)

Модель читается из [CSV-словарей и RDF-данных](Модель%20предметной%20области/Представления%20данных/Словари%20+%20RDF.md):

| Файл                | Что это                              |
| ------------------- | -------------------------------------- |
| `enums.csv`         | Перечисления                          |
| `classes.csv`       | Классы                                |
| `properties.csv`    | Свойства                              |
| `relationships.csv` | Отношения                             |
| `domain.ttl`        | RDF-данные (объекты и их связи) в формате RDF Turtle |

> [!warning]
> При сборке методом `DICT_RDF` **теги не читаются вообще** - `tagsData` остается пустым, даже если файлы `tag_*.loqi` в директории есть.
>
> Этот способ поддерживается для совместимости со старыми доменами. Перевести такой домен на LOQI можно командой [`domain-cli dict-to-loqi`](../4.%20Инструменты/CLI.md#its_domainmodel-domain-cli) - она соберет домен из словарей, запишет его в `domain.loqi` и скопирует рядом файлы графов.

## Теги

**Тег** - это дополнительная часть модели предметной области, применяемая в предметной области только к определенному классу ситуаций. Типичный пример: общая модель описывает понятия, свойственные всей предметной области, а теги - специфику отдельных типов задач.

Имя тега берется прямо из имени файла: `tag_expression.loqi` объявляет тег `expression`.

Тег обычно не используется сам по себе - он **объединяется с общей моделью**:

```java
DomainModel merged = model.getMergedTagDomain("expression");
```
В [CLI](../4.%20Инструменты/CLI.md) выбор тега выполняется опцией `--tag`.

Именно объединенная модель считается полноценной моделью предметной области для соответствующего класса ситуаций. При этом, модель решения задач не обязательно требует наличия каких-либо тегов. Файла общей модели может быть достаточно для многих предметных области.

## Файлы графов

Графы мыслительных процессов читаются независимо от выбранного `BuildMethod` и могут быть заданы в любом из поддерживаемых [представлений](Дерево%20решений/Представления%20дерева.md).

Допустимые имена файлов:

| Шаблон имени                            | Формат                     | Имя графа                |
| --------------------------------------- | -------------------------- | ------------------------ |
| `tree.xml`                              | сериализованный XML        | *(пустое - граф по умолчанию)* |
| `tree_<имя>.xml`, `tpg_<имя>.xml`       | сериализованный XML        | `<имя>`                  |
| `tree.loqi` (устар.)                            | [LOQI2](Дерево%20решений/Способы%20описания/LOQI2.md) | *(пустое - граф по умолчанию)* |
| `tree_<имя>.loqi`, `tpg_<имя>.loqi` (устар.)     | LOQI2                      | `<имя>`                  |
| `<имя>.tpg`                             | LOQI2                      | `<имя>`                  |

### Как определяется имя графа

Имя графа - это ключ, по которому граф достается из модели (в библиотечном коде `model.decisionTree(name)`) и по которому его вызывают [субинтерпретаторы](Дерево%20решений/Субинтерпретаторы.md). Определяется оно из имени файла по следующим правилам:

1. Из имени файла отбрасывается расширение;
2. Если получилось `tree` или `main` - имя графа считается **пустым**. Такой граф является *графом по умолчанию* и доступен в библиотечном коде как `model.getDecisionTree()`;
3. Иначе отбрасывается префикс `tree_` или `tpg_`, и остаток становится именем графа.

Отсюда следуют практические выводы:

- `main.tpg` и `tree.loqi` объявляют один и тот же (безымянный) граф - в одной директории должен быть только один из них;
- `tpg_checkOperands.tpg`, `checkOperands.tpg` и `tree_checkOperands.loqi` дают одно и то же имя графа `checkOperands`;
- расширение `.tpg` не требует префикса, поэтому для новых графов оно наиболее удобно: имя файла совпадает с именем графа.

> [!warning] Об одинаковых именах
> Если в директории окажется несколько файлов, дающих одно и то же имя графа (например, `tree_main.xml` и `tpg_main.tpg`), то в модель попадет только один из них: наборы графов объединяются в порядке XML → LOQI → TPG, и более поздний вытесняет более ранний. Никакого предупреждения при этом не выдается, поэтому дублирующихся имен лучше избегать.

Имя графа, кроме того, определяет и то, как модель записывается обратно в директорию: `writeModelToDirectory` сохраняет граф по умолчанию как `tree.xml`, а именованный - как `tree_<имя>.xml`.

> [!danger] Рекомендуемое расширение для графов мыслительных процессов
> Крайне рекомендуется использовать расширение `.tpg` вместо `.loqi` в новых предметных областях. Расширение `.loqi` оставлено для обратной совместимости и может удалено в будущем

## Валидация

`DomainSolvingModel.validate()` проверяет модель целиком, а не по частям:

1. Валидируется общая модель предметной области;
2. Для **каждого** тега строится объединенная модель, она валидируется, и относительно неё валидируются **все** графы;
	- То есть каждый граф обязан быть корректным относительно любого тега. Это осознанное требование: граф не должен "сломаться" от того, что его применили к ситуации с другим тегом;
3. Если тегов нет вообще, графы валидируются относительно общей модели;
4. Проверяется, что в графах не осталось [отладочных вызовов](Дерево%20решений/Способы%20описания/LOQI2.md#отладочные-вызовы) - если только валидация не запущена в отладочном режиме (`validate(debug = true)`).

Из командной строки то же самое делает команда [`domain-cli validate-dsm`](../4.%20Инструменты/CLI.md#валидация-модели).
